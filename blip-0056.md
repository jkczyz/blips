## Abstract

This bLIP defines a protocol for point-of-sale (PoS) terminals to receive
payment notifications from merchants using BOLT 12 offers and onion messages.
The PoS never touches customer funds and is not on the payment path. The
merchant delegates offer creation to the PoS, which constructs offers containing
notification blinded paths back to itself. When the merchant receives payment,
it notifies the PoS via onion message. An optional `payment_proof` lets the
customer attest the payment directly to the PoS as a fallback.

## Motivation

A merchant wants to accept Lightning payments through a point-of-sale device
(e.g., a physical terminal or web checkout). The PoS must not touch customer
funds: the customer pays the merchant directly, and the PoS has no payment
channels.

The PoS needs to:

- Present an order for the customer to pay
- Display confirmation when the merchant has been paid
- Record payment for accounting and tax purposes

Existing solutions like LNURL with LUD-21 webhooks require centralized callback
servers and introduce trust and privacy trade-offs. This proposal provides a
decentralized alternative built on BOLT 12 and onion messages.

## Specification

### Actors

- **Customer**: Standard BOLT 12 wallet. No sender-side modifications required
  for the base flow. The optional [payment proof](#payment_proof) requires
  wallet support for BOLT 12 payer proofs
  ([bolts#1295](https://github.com/lightning/bolts/pull/1295)).
- **Point-of-Sale (PoS)**: Lightning node without payment channels. Unannounced,
  communicates via onion messages only. It never sees the invoice and is not on
  the payment path.
- **Merchant**: Always-online Lightning node with channel liquidity. Must
  support this notification protocol.


### Terminology

The following terms are used throughout the specification and are
defined in detail in the sections that follow:

| Term | Brief description |
|------|-------------------|
| `offer template` | Amountless, descriptionless offer the merchant creates and hands to the PoS ahead of time; carries the merchant's `offer_issuer_id`, blinded paths to the merchant, and the `payment_notifications` feature bit ([Offer Template](#offer-template)) |
| `per-order offer` | The offer the PoS displays for a single order, built from the template by filling in the amount and description and adding `notification_path` and `payment_token` ([Per-Order Offers](#per-order-offers)) |
| `order_metadata` | Unpredictable per-order value generated by the PoS; carried in the `notification_path` recipient data, which is how the PoS recognises a path as one it built, and sealed in the `payment_token` to make each token ciphertext unique to one order ([Notification Path](#notification-path)) |
| `notification_path` | Blinded onion message path(s) to the PoS, carrying `order_metadata` in the path's recipient data ([Notification Path](#notification-path)) |
| `payment_token` | `amount`, `description`, `notification_path_hash` and `order_metadata`, encrypted to the merchant; the merchant checks them against the invoice request, and its ciphertext is the per-order value both the notification and any payer proof are bound to ([Payment Token](#payment-token)) |
| `payment_notification` | Onion message from the merchant to the PoS at payment time, signed with the merchant's `offer_issuer_id` ([`payment_notification`](#payment_notification)) |
| `notification_ack` / `notification_nack` | PoS response confirming or rejecting the notification, sent over the notification's `reply_path` ([Reply Path](#reply-path)) |
| `payment_proof` | Optional BOLT 12 payer proof sent directly by the customer as a fallback ([`payment_proof`](#payment_proof)) |

### Payment Flow

Ahead of time, the merchant creates an **offer template** — an offer with no
amount or description, naming the merchant's signing key (`offer_issuer_id`) —
and provides it to the PoS. For each order, the PoS completes the template into
a **per-order offer** by filling in the amount and description and adding a
`notification_path` (how the merchant will reach it) and a `payment_token` (the
order's details, sealed to the merchant). The flow begins when the customer
scans that per-order offer.

```
Customer                    Merchant                    PoS
   |                           |                         |
   |  1. scan offer QR code from PoS  ------------------>|
   |                           |                         |
   |  2. invoice_request  ---> |                         |
   |     (via blinded path)    |                         |
   |                           |                         |
   |  3. <--- invoice          |                         |
   |     (with blinded         |                         |
   |      payment paths)       |                         |
   |                           |                         |
   |  4. payment ----------->  |                         |
   |     (via blinded          |                         |
   |      payment path)        |                         |
   |                           |                         |
   |                           |  5. payment_notification|
   |                           |  ---------------------->|
   |                           |     (via notification   |
   |                           |      blinded path)      |
   |                           |                         |
   |                           |  6. notification_ack    |
   |                           |  <----------------------|
   |                           |     (via reply path)    |
   |                           |                         |
   |  7. payment_proof  ---------------------->          |
   |     (optional, via        |                         |
   |      notification path)   |                         |
   |                           |                         |
```

1. **Invoice request**: The PoS has already added `payment_token` and
   `notification_path` to the per-order offer. The customer scans it and
   sends a standard `invoice_request` via the offer's blinded path. The
   merchant identifies the template and applies the checks in [Invoice
   Requests](#invoice-requests). None of those checks authenticate the
   requester — anyone can seal a `payment_token` to the merchant's public
   `offer_issuer_id` — so they are consistency filters that let the merchant
   refuse a malformed or internally inconsistent request. It then issues an
   invoice carrying the same `payment_token` ciphertext.

2. **Payment**: The customer pays the invoice via the blinded payment paths.
   Standard BOLT 12, no sender-side modifications required.

3. **Notification**: Once the payment has settled, the merchant sends a
   `payment_notification` onion message to the PoS via the `notification_path`,
   signed with the `offer_issuer_id` the order's offer named, and including a
   `reply_path` for the response (see [Reply Path](#reply-path)). The merchant
   retries with backoff until acknowledged, up to an implementation-defined
   limit, escalating to manual reconciliation if retries are exhausted. (See
   [`payment_notification`](#payment_notification).)

4. **Acknowledgement**: The PoS identifies the order from the arrival path,
   verifies the signature against that order's issuer key, checks that the
   notification names that order's own `payment_token` ciphertext, and answers
   over the notification's `reply_path` with `notification_ack` or
   `notification_nack` (or, for a notification whose signature does not verify,
   not at all).

5. **Optional payment proof**: The customer MAY send a `payment_proof` directly
   to the PoS as a fallback. (See [`payment_proof`](#payment_proof).)

### Security Model

Onion messages carry no sender authentication, and the `notification_path`
ships inside the offer, so any party holding the per-order offer can send a
`payment_notification` down it. A notification's payment hash and preimage
authenticate nothing on their own: the PoS never sees the invoice, so it cannot
distinguish a released preimage from a random one.

Authenticity therefore rests on two checks, which answer two different
questions and are both required:

- **Who sent this?** The BIP340 `signature`, verified against the
  `offer_issuer_id` of the template the order was built from. Only the merchant
  holds that key, so only the merchant can produce a notification the PoS will
  look at. Verifying against *that order's* key rather than any known key is
  part of the requirement: see
  [`payment_notification`](#payment_notification).
- **Which order is it for?** `payment_token_hash`, compared against the SHA256
  of the ciphertext the PoS sealed for the order that owns the arrival path.
  The signature says a payment happened; only this says which order it settled.

Both are necessary. Drop the signature and anyone holding the offer can claim
the order is paid, since every other field is either public or unverifiable.
Drop the token hash and one payment credits every order at or below its amount,
and a customer who assembles their own offer around a token of their own passes
every check.

Nothing in the notification is secret, and nothing needs to be:
`payment_token_hash` is a hash of a value that ships in the offer, the invoice,
and any payer proof, and the preimage is worthless to anyone who cannot claim
the payment. Forgery resistance comes from the signing key, not from
concealment, which is why this version of the protocol makes no confidentiality
demand on the notification payload and why an attacker occupying the PoS's
introduction node learns nothing worth having by forwarding one. The token's
plaintext is a different matter — it still must stay concealed, for the reasons
given in [Payment Token](#payment-token).

The `payment_token` ciphertext, in turn, proves nothing about who created it.
`Enc` is to the merchant's public `offer_issuer_id`, and the offer template may
be public, so anyone can seal a self-consistent token over fields of their
choosing — including over another order's `notification_path`. No merchant-side
check can detect this, because both sides of every comparison the merchant
makes come from the requester. What the ciphertext *does* provide is a value
only the PoS can produce for a given order, which is what the
`payment_token_hash` check rests on.

The protocol authenticates notifications against a malicious customer; it does
not protect the PoS against the merchant node. The PoS trusts the merchant for
the truthfulness of `notification_amount`, for the notification being sent at
all, for notifications being sent only for orders actually paid, and for not
disclosing the sealed order fields. A cooperating customer's
[`payment_proof`](#payment_proof) removes the trust in the notification being
sent at all, since the proof is merchant-signed and order-bound; it does not
remove trust for notifications the merchant fabricates.

A signed `payment_notification` is **not** proof of payment, and MUST NOT be
presented as one. The merchant signs it with its own key and chooses the
hash/preimage pair it contains, so it can mint a perfectly valid notification
for an invoice nobody paid. What the signature establishes is attribution:
whoever holds the notification can show that *this merchant* asserted *this
order* was paid. That is what makes it useful evidence in a reconciliation
dispute, and it is strictly weaker than the [`payment_proof`](#payment_proof),
which carries the payer's own signature.

Nor does the protocol bound *who* may ask the merchant to invoice a per-order
offer. Anyone holding the template — which may be public via BIP 353 — can seal
a token of their own, over any `notification_path` value they like, and have
the merchant issue an invoice, claim the payment, and send a signed
notification down that path. The PoS refuses the result, because the token is
not the ciphertext it sealed, so no order is credited; but the merchant has
settled a payment for an order that does not exist, and its order book and
reconciliation queue can be polluted at the cost of the sealed amounts.

Signing raises the stakes on this gap rather than closing it: the merchant is
now a notification-signing service for whatever `notification_path` a stranger
names, and nothing lets it tell a PoS-built offer from an assembled one.
Closing it needs an authentication cookie in `offer_metadata`, MACed under a
key shared at template hand-off; see [Open Questions](#open-questions).

### Offer Template

The merchant creates an **offer template** and provides it to the PoS:

- Amountless, no description (filled per-order by the PoS)
- Contains blinded paths to the merchant for invoice requests
- Includes `offer_issuer_id` (the merchant's offer signing key)
- Sets the `payment_notifications` feature bit in `offer_features` to signal to
  the PoS that the merchant supports the protocol:

| Bit  | Name                     | Description |
|------|--------------------------|-------------|
| 265 (odd)  | `payment_notifications`  | The merchant supports this protocol and will deliver a `payment_notification` for per-order offers carrying a `notification_path` and `payment_token` |

#### Requirements

The merchant:

- MUST include `offer_issuer_id` in the template.
- MUST NOT set `offer_chains`, `offer_currency`, or `offer_quantity_max` on the
  template.
- MAY refresh the template periodically to rotate blinded paths.
- MAY publish the template via a BIP 353 address (e.g., `vincenzo@hedwig.sh`)
  that resolves to it.

The PoS:

- MUST NOT use a template that carries an amount or description, lacks blinded
  paths to the merchant for invoice requests, omits `offer_issuer_id`, sets
  `offer_chains`, `offer_currency`, or `offer_quantity_max`, or does not set
  the `payment_notifications` feature bit.

#### Rationale

`offer_chains`, `offer_currency`, and `offer_quantity_max` are excluded because
the merchant's own checks (see [Invoice Requests](#invoice-requests)) reject
per-order offers carrying any of these, so a template setting them yields
offers the merchant itself refuses. A merchant that accepts non-bitcoin chains
elsewhere must publish a separate, bitcoin-only template for PoS use.

With a BIP 353 address the PoS can be configured once: it resolves the address
to obtain a fresh template whenever it needs one, and the merchant (or its
wallet vendor) keeps the resolved offer up to date with fresh blinded paths.
The merchant still has to refresh those paths, but the PoS doesn't need to be
re-configured each time.

### Per-Order Offers

For each order, the PoS constructs a complete offer from the template by
adding:

1. **Amount**: the order total, denominated in millisatoshis
2. **Description**: human-readable order description (REQUIRED; BOLT 12
   requires `offer_description` for amount-bearing offers)
3. **Expiry**: an `offer_absolute_expiry` bounding the order's lifetime
   (RECOMMENDED)
4. **`notification_path`**: one or more blinded paths back to the PoS
5. **`payment_token`**: the order fields and `order_metadata` encrypted to the
   template's `offer_issuer_id`, constructed as defined in [Payment
   Token](#payment-token)

The last two are new offer TLVs:

| Type | Name | Description |
|------|------|-------------|
| 1000000001 (odd)  | `notification_path` | Blinded onion message path(s) to the PoS. `order_metadata` is carried in the path's recipient data. |
| 1000000003 (odd)  | `payment_token` | `amount`, `description`, `notification_path_hash` and `order_metadata` encrypted to the offer's `offer_issuer_id`; the merchant checks them against the invoice request, and the notification commits to this value's SHA256 (see [Payment Token](#payment-token)). |

The `payment_notifications` feature bit is inherited from the template and
remains set. The PoS presents this offer to the customer as a QR code or over
any other transport the PoS supports (e.g., NFC, BLE).

#### Requirements

A PoS constructing a per-order offer:

- MUST NOT set `offer_currency` (currency-denominated offers are out of scope),
  MUST NOT set `offer_quantity_max`, and MUST NOT set `offer_chains`, so that
  the order total is exactly the amount sealed in the `payment_token`
  (per-order offers are bitcoin-only, and BOLT 12 takes an absent
  `offer_chains` to mean bitcoin).
- MUST present exactly one per-order offer per order: one `notification_path`
  TLV value and one `payment_token` ciphertext, identical across every
  transport it offers the order over. A PoS that must vary the presentation
  MUST instead retain every (`notification_path` value, `payment_token`
  ciphertext) pair it presented for the order and accept a notification or
  proof matching any of them.
- SHOULD limit the offer to a single notification path when presenting it as a
  QR code.
- MUST retain, per order: the `order_metadata`, the `payment_token` ciphertext
  it placed in the offer, the expected amount, the order's expiry (if any), the
  `offer_issuer_id` of the template the order was built from, and — once the
  order is paid — the `payment_hash` of the payment that settled it.
- MUST retain that state for an implementation-defined period after the order
  settles or expires, rather than discarding it immediately.
- SHOULD retain an accepted notification's signed records and its `signature`
  for at least as long as it retains the order state.

#### Rationale

##### Type numbers

Both offer TLV types must fall inside the ranges BOLT 12 permits in an offer —
1 to 79 and 1000000000 to 1999999999 — because an offer reader must not respond
to an offer carrying anything outside them, and an `invoice_request` reader
must reject a request carrying a non-signature field outside 0 to 159 and
1000000000 to 2999999999. A number outside those ranges would make every
conformant merchant reject every request this protocol produces. Both are odd
so that an unmodified BOLT 12 wallet ignores them as unknown-but-tolerated
rather than refusing the offer, while still copying them into the
`invoice_request` as BOLT 12 requires of all offer fields.

The type numbers defined in this document — the offer TLVs above and the
[onion message types](#onion-message-types) — are chosen to satisfy the range
constraints the containing stream places on them, and are to be reserved in
[bLIP 2](./blip-0002.md).

##### One offer per order

Presenting two variants — say a single-path value in a QR code and a multi-path
value over NFC — gives the order two distinct ciphertexts, and both the
notification the merchant signs and any payer proof commit to whichever variant
the customer actually used. The PoS would then reject a genuinely paid order
because it compared against the other variant.

The QR guidance exists because the blinded paths and the token ciphertext make
the offer noticeably larger.

##### Retained state

Every check the PoS performs on a notification or a payment proof compares
against this state; the ciphertext in particular cannot be re-derived if `Enc`
is randomized. Retaining the state past settlement or expiry lets a retried
notification for an order already paid be re-acked and a late one be answered
`order_expired` rather than `unknown_order`.

The `offer_issuer_id` in that list is the key the PoS verifies notification
signatures against; see [`payment_notification`](#payment_notification) for why
it must come from this state and from nowhere else.

An accepted notification's signed records and `signature` are the only artifact
in this protocol that a third party can verify against the merchant's published
`offer_issuer_id`, which makes them the useful evidence in the reconciliation
dispute this protocol exists to avoid.

### Notification Path

The `notification_path` is a standard onion message blinded path to the PoS,
constructed per-order.

The path's recipient data — the data the PoS encrypts to itself when it builds
the blinded path — carries `order_metadata`: an opaque `byte..` sequence defined
by the PoS. This data is encrypted during blinded path construction and can only
be decrypted by the PoS. The PoS uses it to identify which order an incoming
message belongs to, and to recognise the arrival path as one it built itself.
The path's recipient data is opaque to the merchant — it never learns
`order_metadata` from the path — though the merchant does parse the
`notification_path` value into blinded paths, hash it verbatim, and select a
path to send over (see [Invoice Requests](#invoice-requests)).

#### Requirements

The PoS:

- MUST construct the `notification_path` per order; it MUST NOT be part of the
  offer template.
- MUST use the path only for its intended purpose: receiving
  `payment_notification` and `payment_proof` messages for this one order.
- MUST include in `order_metadata` at least 16 bytes (128 bits) that are
  unguessable to any other party: fresh output of a cryptographically secure
  random number generator, or an equally long output of a keyed pseudorandom
  function (such as HMAC) over an order identifier, keyed with a secret known
  only to the PoS. Alternatively `order_metadata` MUST carry a MAC, under a key
  known only to the PoS, over whatever handle it encodes.
- MUST NOT compute that component from values known to or predictable by the
  customer — order sequence numbers, timestamps, amounts, descriptions —
  without mixing in a secret known only to the PoS. A bare hash or encoding of
  such values is not acceptable; what makes the keyed-PRF construction above
  safe is the key, not the input.
- MUST generate a fresh `order_metadata` for each order and MUST NOT reuse a
  value across orders, including across restarts, state restores, and across
  terminals sharing one node id. A PoS using the keyed-PRF construction MUST
  NOT reuse the order identifier across orders; the CSPRNG construction
  satisfies this requirement unconditionally.
- SHOULD prefer the keyed-PRF or MAC form over a bare CSPRNG value.
- MAY encode additional PoS-private fields (for example, order correlation or
  expected amount) alongside the unguessable component using an internal format
  such as TLVs, and these MUST NOT reduce its entropy; this bLIP does not
  define the contents. The PoS MUST NOT encode the notification verification
  key, or an index to it, among them (see
  [`payment_notification`](#payment_notification)).
- MUST NOT leak information about stored values through timing in the
  comparison that maps an arrival path's `order_metadata` to an order.

#### Rationale

##### Path authentication

`order_metadata` is this protocol's `path_id` in the sense of BOLT 4, which
requires a blinded path's final recipient to ignore a message whose recipient
data does not correspond to a path it created, and which requires that data to
contain information the sender cannot have access to. That requirement is not
satisfied by uniqueness alone. Blinded path recipient data is encrypted *to* the
PoS, not authenticated as having been created *by* it: any party that learns the
PoS's node id can pick its own path key, derive the encryption key, and write
recipient data of its own choosing. The PoS's node id is not hard to come by — it
is absent from channel gossip, not secret. The introduction node named in
cleartext in every per-order offer is a direct peer of a channel-less PoS, a
one-hop notification path puts the node id in the offer outright, and the PoS
reveals it to any node it dials to deliver a response over a `reply_path`.

What `order_metadata` does *not* do, in this version of the protocol, is
authenticate a notification. That rests on the merchant's signature (see
[Security Model](#security-model)). What it prevents is an attacker-chosen
arrival path being accepted as one the PoS built, which would otherwise turn
the reason codes into a remote order log: an attacker who can guess the handle
learns whether an order exists, when it was created, and — from `order_expired`
versus silence — whether it was paid or abandoned, giving a revenue and
conversion feed on the merchant's till from outside the shop.

##### Recognising paths after a state loss

The keyed-PRF or MAC form is preferred over a bare CSPRNG value because only
those forms let the PoS tell a path it built from an attacker-built one *after*
it has lost its order table, which is what makes the `unknown_order` response
in [Reply Path](#reply-path) meaningful rather than an oracle.

##### Timing

The comparison that maps an arrival path's `order_metadata` to an order is the
one comparison in the protocol that touches a secret, so a lookup structure
with value-dependent timing (for example byte-wise comparison down a sorted
array, or a radix trie) can expose a prefix oracle on live handles to any party
that can reach the PoS over a path of its own.

### Payment Token

When the PoS adds a `payment_token` TLV to the per-order offer, the token seals
the order's identity, encrypted to the template's `offer_issuer_id`:

```
payment_token = Enc(offer_issuer_id, sealed_order)
```

`sealed_order` contains:

- `amount`: the offer amount in millisatoshis
- `description`: the offer description
- `notification_path_hash`: SHA256 over the exact octets the PoS places in the
  `notification_path` TLV value of the same offer (the value only, not the type
  and length)
- `order_metadata`: the per-order unguessable value

`amount` and `description` are the cleartext offer fields the merchant verifies
against the invoice request. `notification_path_hash` lets the merchant detect a
`notification_path` that was swapped without re-sealing the token.
`order_metadata` is the same per-order value the PoS places in the
`notification_path` recipient data. The merchant decrypts the token, performs
the checks in [Invoice Requests](#invoice-requests), and commits to the token's
*ciphertext* in the notification it signs; it never relays the plaintext.

#### Requirements

The PoS:

- MUST encrypt to the `offer_issuer_id` from the offer template.
- MUST
  [tlv encode](https://github.com/lightning/bolts/blob/master/01-messaging.md#type-length-value-format)
  the plaintext inside `payment_token`, and MAY add PoS-private records to it
  (a terminal or cashier identifier, an internal order key).

`Enc`:

- MUST be an authenticated encryption scheme.
- MUST conceal the plaintext from every party other than the merchant.

The merchant:

- MUST decrypt with the private key corresponding to `offer_issuer_id`.
- MUST NOT disclose the decrypted `sealed_order`, or any part of it, to any
  party. In particular it MUST NOT appear in an `invoice_error` — including as
  an `erroneous_field`/`suggested_value` pair naming the sealed amount or
  description — in the invoice (which carries only the ciphertext), in an
  operator-visible receipt reachable by the payer, or in any other data
  reachable by a party other than the PoS.

#### Rationale

##### Why encrypt to `offer_issuer_id`

Encrypting to the template's `offer_issuer_id` matches the BOLT 12 rule that
`invoice_node_id` equals `offer_issuer_id` when present, and avoids encrypting
to a last-hop `blinded_node_id` (which the PoS cannot know at offer-construction
time and which may differ across `offer_paths`).

##### Why authenticated encryption

Authentication lets the merchant tell a token it can act on from a corrupted or
truncated one, and integrity-protects the PoS-private records as well as
concealing them.

##### Why the plaintext stays concealed

The per-order `amount` and `description` are not public: only the amountless,
descriptionless template is published, while the per-order offer is shown to one
customer at the counter. The ciphertext, by contrast, travels into the invoice
and into any payer proof built over it, where it outlives the offer. Encrypting
it is what stops that ciphertext from becoming a bearer token that anyone
holding a proof can present to the merchant to recover the order's amount and
description — the very fields BOLT 12's merkle nonce leaves exist to let a payer
redact.

Without the merchant's non-disclosure rule the merchant is an unsealing oracle:
anyone holding a payer proof can extract the ciphertext, submit it in an
`invoice_request` with fields that deliberately mismatch, and read the sealed
amount and description back out of the error — recovering exactly what the
payer redacted.

##### Why `order_metadata` is sealed

Including `order_metadata` is what makes each order's ciphertext distinct.
Without it `sealed_order` would be `{amount, description, notification_path_hash}`,
and two orders would collide whenever the amount and description repeat — the
normal case at a till selling the same item at the same price. The
`notification_path_hash` is not a sufficient substitute on its own: nothing in
BOLT 4 requires a blinded path's bytes to differ between constructions (the
ephemeral key is only a SHOULD-be-random value), and this bLIP does not require
`Enc` to be randomized. `order_metadata` is required to be fresh per order
unconditionally, so it carries the distinctness that the notification and payer
proof checks both depend on.

##### Token provenance

The token carries no proof of origin: `offer_issuer_id` is a public key, so
anyone can seal a well-formed `payment_token` over fields of their choosing,
including over another order's `notification_path` value. Checks on the token's
contents are therefore consistency checks and not authentication of the
requester (see [Security Model](#security-model)). What binds a notification
or a proof to an order is that it names the ciphertext *the PoS itself* sealed,
which no other party can produce.

### Invoice Requests

BOLT 12 requires an `invoice_request` reader to reject unless "the offer fields
do not exactly match a valid, unexpired offer". A merchant implementing this
bLIP cannot apply that rule to a per-order offer: the offer was built by the PoS
and the merchant has never seen it. The requirements below replace that check
for an `invoice_request` carrying a `payment_token`. Everything else BOLT 12
requires of an `invoice_request` reader still applies.

The merchant's view of a per-order offer is only what the `invoice_request`
carries, and the PoS-added offer fields are not signed by anyone.

The invoice carries `payment_token` at the same type number, 1000000003.

#### Requirements

A reader of an `invoice_request` (the merchant):

- MUST reject an `invoice_request` that carries a `notification_path` without a
  `payment_token`.
- MUST reject an `invoice_request` carrying a `payment_token` unless all of the
  following hold:
  - `offer_issuer_id` is present and is one of the merchant's own issuer keys
    (this is how the merchant identifies the template), and the `payment_token`
    decrypts and authenticates under that key's private half
  - `offer_amount` is present and equals the token's `amount`;
    `offer_description` is present and equals the token's `description`. Both
    comparisons are over the raw TLV value octets, with no normalization.
  - `offer_currency` and `invreq_quantity` are absent (per-order offers are
    millisatoshi-denominated and single-item)
  - `offer_chains` is absent, and `invreq_chain` is either absent or the
    bitcoin chain hash
  - `notification_path` is present, parses as one or more non-empty
    `blinded_path`s, and hashes to the token's `notification_path_hash`. The
    merchant MUST hash the octets of the `notification_path` TLV value exactly
    as received, without parsing and re-serializing them.
  - The amount the merchant would invoice (`invreq_amount` when present,
    otherwise `offer_amount`) is at least the token's `amount`
- if it does not reject an `invoice_request` carrying a `payment_token`:
  - MUST copy the `payment_token` TLV value from the `invoice_request` into the
    invoice byte-for-byte; it MUST NOT re-encode or re-seal it.
  - MUST be able to determine, at settlement, the `payment_token` ciphertext
    and the `notification_path` value from the `invoice_request` it invoiced.
    It MAY retain them, or carry what it needs in the recipient data of the
    blinded payment paths it puts in the invoice; such an implementation SHOULD
    carry the 32-byte SHA256 of the `payment_token` value rather than the value
    itself, and MUST NOT carry the `notification_path` value.

Any reader that forwards the `notification_path` value:

- MUST copy it unchanged. In particular it MUST NOT re-encode a
  `blinded_path`'s `first_node_id` between the two forms `sciddir_or_pubkey`
  permits.

#### Rationale

##### What the path-hash check catches

The `notification_path_hash` check is worth stating precisely, because it is
narrower than it looks. It catches a `notification_path` that was replaced while
the original `payment_token` was left in place — the cheapest form of tampering
with the channel the offer travels over, and the one an attacker who cannot seal
a token is limited to. It does **not** catch an attacker who re-seals: anyone
can seal a fresh token to the merchant's public `offer_issuer_id` over any
`notification_path` value they like, and every check in this section then passes
by construction, because both sides of every comparison are theirs. Detecting
*that* requires the merchant to be able to tell a PoS-built offer from one a
stranger assembled, which this bLIP does not yet provide; see [Open
Questions](#open-questions). What limits the damage in the meantime is that the
notification commits to the token ciphertext, so a re-sealed token cannot cause
the PoS to credit an order (see
[`payment_notification`](#payment_notification)) — it can only cost the
merchant a settled payment for an order that does not exist.

##### Denomination

Pinning the denomination — no `offer_currency`, no `offer_chains`, no
non-bitcoin `invreq_chain` — keeps the amount comparison well-defined: BOLT 12
computes the expected amount in the `invreq_chain` currency, so a customer who
requested a chain the merchant also supports could otherwise pay the order
total in another chain's units and still satisfy every amount check here and at
the PoS.

##### The invoice's `payment_token`

No separate invoice requirement is needed for `payment_token` to reach the
invoice: BOLT 12 already obliges an invoice writer to copy all non-signature
fields from the `invoice_request`, including unknown ones, so the ciphertext
reaches the invoice — and therefore any payer proof built over it —
automatically. The byte-for-byte rule exists because the payer proof's
ciphertext-equality check (see [`payment_proof`](#payment_proof)) compares the
invoice's copy against the ciphertext the PoS sealed, so a re-sealed copy —
even to the same plaintext, under a randomized `Enc` — would fail every proof.

##### Stateless merchants

The settlement obligation is a capability requirement, not a retention mandate:
an implementation that does not keep invoices instead carries what it needs in
the recipient data of the blinded payment paths it authors, which returns to it
inside the payment onion. The payment onion has a fixed 1300-byte budget with
no larger variant, and even a minimal two-hop blinded path consumes a large
fraction of it — which is why such an implementation carries the token's
32-byte hash rather than the value, and never the path.

##### Forwarding without re-encoding

Because the hash covers the `notification_path` value byte for byte, any reader
that forwards the value must not normalize it. An unmodified BOLT 12 payer
satisfies this, since BOLT 12 requires it to copy all offer fields into the
`invoice_request` unchanged; the requirement matters for readers that
understand `notification_path` and might normalize it.

### Onion Message Types

The following `onionmsg_tlv` payload types are defined:

| Type | Name | Description |
|------|------|-------------|
| 65540  | `payment_notification` | Notification from merchant to PoS (see payload below) |
| 65542  | `notification_ack` | Positive acknowledgement from PoS, echoing the notification's `payment_hash` |
| 65544  | `notification_nack` | Negative acknowledgement from PoS, echoing the notification's `payment_hash` and carrying a reason code |
| 65546  | `payment_proof` | Optional BOLT 12 payer proof ([bolts#1295](https://github.com/lightning/bolts/pull/1295)) from customer to PoS (see [`payment_proof`](#payment_proof)) |

These are `onionmsg_tlv` payload types, so they must be 64 or above, and each
message carries exactly one of them: BOLT 4 requires a recipient to ignore an
`onionmsg_tlv` containing more than one payload field.

### `payment_notification`

`payment_notification` is a TLV stream, signed by the merchant the way BOLT 12
signs its own forms:

1. `tlv_stream`: `payment_notification`
2. types:
    1. type: 0 (`notification_metadata`)
    2. data:
        * [`...*byte`:`blob`]
    1. type: 2 (`payment_token_hash`)
    2. data:
        * [`sha256`:`hash`]
    1. type: 4 (`notification_payment_hash`)
    2. data:
        * [`sha256`:`payment_hash`]
    1. type: 6 (`notification_preimage`)
    2. data:
        * [`32*byte`:`preimage`]
    1. type: 8 (`notification_amount`)
    2. data:
        * [`tu64`:`msat`]
    1. type: 240 (`signature`)
    2. data:
        * [`bip340sig`:`sig`]

- `notification_metadata` is an unpredictable series of bytes chosen by the
  merchant, fresh per notification.
- `payment_token_hash` is SHA256 over the `payment_token` TLV value as it
  appeared in the `invoice_request` the merchant invoiced (the value only, not
  the type and length).
- `notification_payment_hash` and `notification_preimage` are the payment hash
  and the preimage the merchant released.
- `notification_amount` is the amount actually claimed, in millisatoshis — not
  the amount invoiced.

#### Signature Calculation

`signature` is computed exactly as BOLT 12 computes its signatures: the tag is
`"lightning"` || `"payment_notification"` || `"signature"` and the message is the
merkle root over the stream's non-signature TLV records, with each record's leaf
paired with a nonce leaf as BOLT 12 specifies. The key is the private half of the
`offer_issuer_id` from the offer the `invoice_request` carried.

#### Requirements

A writer of `payment_notification` (the merchant):

- MUST NOT send a `payment_notification` for any `invoice_request` it rejected.
- MUST NOT send a `payment_notification` before the payment has settled.
- MUST set `notification_metadata` to an unpredictable value, fresh per
  notification.
- MUST set `payment_token_hash` to SHA256 over the `payment_token` TLV value as
  it appeared in the `invoice_request` it invoiced.
- MUST set `notification_payment_hash` and `notification_preimage` to the
  payment hash and preimage of the settled payment.
- MUST set `notification_amount` to the amount actually claimed, not the amount
  invoiced.
- MUST specify exactly one signature TLV element, `signature`, computed as
  described in [Signature Calculation](#signature-calculation).
- MUST send the `payment_notification` over a path contained in the
  `notification_path` TLV value whose hash the token commits to, and MUST NOT
  send it over any other path. It MAY use a different path from that value for
  each retry, and SHOULD NOT send more than one copy at a time, so that one
  notification corresponds to one expected acknowledgement.
- MUST include a `reply_path` in the onion message (see [Reply
  Path](#reply-path)).
- SHOULD retry with backoff until acknowledged, up to an implementation-defined
  limit, and SHOULD escalate to manual reconciliation if retries are exhausted
  without a response.

Several of the checks below assign a **reason code**; the codes, and how a
`notification_nack` delivers them, are defined in [`notification_ack` and
`notification_nack`](#notification_ack-and-notification_nack).

A reader of `payment_notification` (the PoS):

- MUST parse the stream per BOLT 1: strictly increasing types, minimally
  encoded lengths. A reader encountering an unknown even type MUST ignore the
  message.
- MUST verify the notification as a complete stream; neither party may
  selectively disclose a subset of its records with the signature. The PoS MUST
  reject a notification that omits `notification_metadata`, and MUST NOT treat
  any absent required record as a default value.
- MUST identify the order from the `order_metadata` in the **arrival path's**
  recipient data, and only from there. If no order it created owns the arrival
  path, the reason code is `unknown_order`.
- MUST compute the merkle root over every non-signature record in the stream,
  including records it does not understand.
- MUST verify `signature` against the `offer_issuer_id` of the template **that
  order's** offer was built from — not merely some issuer key the PoS knows —
  taken from the PoS's own per-order state. It MUST NOT take the verification
  key, or an index to it, from the arrival path's recipient data or from any
  other value carried in the notification or the path. If the signature does
  not verify, the PoS MUST NOT respond at all and MUST NOT treat the order as
  paid.
- MUST verify that SHA256(`notification_preimage`) equals
  `notification_payment_hash`. Otherwise the reason code is
  `preimage_mismatch`: a signed notification carrying a mismatched pair is
  worthless as evidence, and nothing else in the protocol would catch it.
- If that order is already marked paid and `notification_payment_hash` equals
  the one recorded for it, MUST respond with `notification_ack` and stop —
  regardless of expiry. The PoS MUST credit an order at most once. If the order
  is paid but the payment hash differs, it runs the remaining checks (skipping
  expiry): if they pass, the customer paid twice — the PoS acks, but SHOULD
  flag the order for operator attention rather than absorb the second payment
  silently; if they fail, it treats the notification as any other failing one.
- If the order is past its expiry, the reason code is `order_expired`. The PoS
  SHOULD apply a grace period beyond `offer_absolute_expiry` covering invoice
  expiry plus payment and notification latency. An order with no
  `offer_absolute_expiry` never becomes `order_expired`.
- MUST verify that `payment_token_hash` equals SHA256 over the `payment_token`
  ciphertext the PoS sealed into that order's offer. Otherwise the reason code
  is `order_mismatch`.
- MUST verify that `notification_amount` is at least that order's expected
  amount. Otherwise the reason code is `amount_insufficient`.
- MUST NOT treat the order as paid on a notification failing any of these
  checks. Whether the PoS answers at all is governed by [Reply
  Path](#reply-path).

#### Rationale

##### Verifying against that order's key

A PoS serving more than one merchant, or holding a rotated template, that
verified against any known key would let one merchant mark another merchant's
order paid: photograph the order's offer, build a notification with a random
hash/preimage pair and the order's total, sign it with your own issuer key, and
send it down the path in the offer. No payment and no invoice request required.

The key must come from the PoS's own per-order state for the same reason.
Blinded path recipient data is encrypted to the PoS but is not authenticated as
having been created by it (see [Notification Path](#notification-path)), so a
key read from there is a key the sender chose: an attacker who knows the PoS's
node id builds its own path to the PoS, writes an order identifier and a
keypair of its own into the recipient data, and signs a notification that then
verifies. That marks the order paid with no payment and no contact with the
merchant at all. The same applies to an index into a table of keys, which any
co-tenant merchant whose key the PoS knows can point at itself.

##### Committing to the token ciphertext

The `payment_token_hash` check is what ties the merchant's signature to *this*
order. The signature alone attests only that the merchant received some payment;
it says nothing about which order the payment settled, so without this check one
payment would credit every order at or below its amount — place two identically
priced orders, pay one, and replay the signed notification down the second
order's path. It also stops a customer who re-seals the token: only the PoS can
produce the ciphertext it sealed, so an offer assembled by anyone else yields a
notification the PoS refuses, even though every merchant-side check passed. This
is why the PoS compares the ciphertext rather than the path hash — the path hash
is computable by any offer holder, while the ciphertext is not.

A customer who tampers with the offer before paying is therefore caught at the
PoS, not at the merchant. The merchant rejects an `invoice_request` whose
cleartext offer fields do not match the decrypted token and does not invoice
less than the token's `amount` (see [Invoice Requests](#invoice-requests)), but
a customer who re-seals the token over the tampered fields passes both. The
authoritative check is `payment_token_hash`: a re-sealed token is not the
ciphertext the PoS sealed, so the notification is rejected with `order_mismatch`
and the tampered order is never shown as paid. A genuine notification reporting
a short amount is rejected with `amount_insufficient`. In both cases the
merchant has already claimed the payment, so — per the nack rules — it escalates
to manual reconciliation rather than retrying.

This is worth being concrete about, because the failure it prevents is not only
under-payment. Without the ciphertext check, a customer could pay the correct
amount for a real order while having the merchant invoice an arbitrary
`description` of their choosing: the PoS would credit the real order, the goods
would be released, and the merchant's records — and any payer proof built over
that invoice — would attest a purchase of something else entirely.

##### `notification_metadata` and the merkle nonce

BOLT 12's merkle construction supports selectively disclosing a subset of
records with the signature for `invoice`, but only because `invreq_metadata`
sits at type 0 and is unpredictable, which is what makes the nonce leaves
unguessable. `notification_metadata` occupies type 0 here for the same reason.

##### Extensions and the signature range

Records in the 240 to 1000 range are excluded from the merkle root, so a second
record in that range would leave the root implementation-defined; hence exactly
one signature element. Hashing every non-signature record, including
unrecognised ones, is what lets this message be extended: a reader that hashes
only recognised records rejects every future extension of this message. The
BOLT 1 parse rule is stated here because BOLT 4 imposes the unknown-even-type
rule on the outer `onionmsg_tlv`, not on a payload nested inside it.

##### The amount claimed

Sending the invoiced amount would make the PoS's sufficiency check compare a
value against itself, so it could never fire.

##### Settlement, not claim

A payment that is merely claimable can still fail, and a notification sent at
that point can announce a payment the merchant never receives.

##### Already paid, expiry, and double payment

The already-paid re-ack exists so that a lost or delayed acknowledgement does
not escalate a correctly credited order to manual reconciliation. The expiry
grace period exists because a customer who fetched the invoice just before
offer expiry pays a merchant that has already claimed the funds, and nacking
that payment creates the very reconciliation case the protocol exists to avoid.

### `notification_ack` and `notification_nack`

The `notification_ack` and `notification_nack` payloads contain:

1. data:
   * [`sha256`:`payment_hash`]
     * Echo of the notification's `payment_hash`, for correlation (see
       [Reply Path](#reply-path))

with `notification_nack` additionally containing:

2. data:
   * [`byte`:`reason`]
     * A reason code from the table below. A merchant receiving an
       unrecognized code treats it as a terminal failure.

A `notification_nack` carries a one-byte reason code so the merchant's
reconciliation report can say why the notification was refused:

| Code | Name | Meaning |
|------|------|---------|
| 0 | `unknown_order` | No order at the PoS owns the arrival path |
| 1 | `order_expired` | The order is past its expiry |
| 2 | `order_mismatch` | The signature verified, but `payment_token_hash` is not the hash of the ciphertext the PoS sealed for the order that owns the arrival path |
| 3 | `amount_insufficient` | Notified `notification_amount` is below the expected order amount |
| 4 | `preimage_mismatch` | SHA256(`notification_preimage`) does not equal `notification_payment_hash` |

#### Requirements

A writer of `notification_ack` or `notification_nack` (the PoS):

- MUST echo the `notification_payment_hash` of the notification it responds to,
  so correlation does not rest on the path alone.
- MUST NOT send `order_mismatch` or `preimage_mismatch` for a notification
  whose signature did not verify.

A reader of `notification_ack` or `notification_nack` (the merchant):

- has already claimed the payment when a nack arrives; it SHOULD report the
  failure to its operator for manual reconciliation rather than retry.
- MAY retry on `unknown_order`, which may mean the PoS lost its state (e.g. a
  restart), and escalates if it recurs.

#### Rationale

`order_mismatch` and `preimage_mismatch` always indicate a bug in the sender,
never a forgery: the signature verified against the order's own issuer key, so
the merchant itself signed a notification naming one order and sent it down
another order's path, or signed a preimage that does not match the payment hash
beside it. Sending either code for a notification whose signature did not
verify would answer an unattributable message, telling an unknown party that
the arrival path is live.

### Reply Path

The PoS has no payment channels and no gossip view of the network, so it
cannot construct a route back to the merchant on its own. Per BOLT 4, an onion
message recipient can only respond over a `reply_path` supplied by the sender,
and it replies by delivering the onion directly to the path's `first_node_id`.

#### Requirements

The merchant:

- MUST include a `reply_path` in every `payment_notification`.
- MUST express the `reply_path`'s `first_node_id` in pubkey form (not the
  short-channel-id form, which only a node with gossip can resolve), and SHOULD
  root the path at the introduction node of the `notification_path` it is
  sending over — a node the PoS is demonstrably reachable from — or at another
  node it has reason to believe the PoS can reach. A reply address the PoS
  cannot deliver to is as good as none.
- MUST construct a fresh `reply_path` for each `payment_notification` — fresh
  per notification, not necessarily per retry — and place an identifier for
  that notification (a `path_id`, per BOLT 4) in the path's recipient data.
  That identifier MUST contain at least 16 bytes (128 bits) unguessable to any
  other party, or MUST carry a MAC over the handle under a key known only to
  the merchant.
- MUST NOT reuse a `reply_path` for a different notification, and MUST NOT
  reuse its `offer_paths` as a `reply_path`. Retries of the same notification
  MAY reuse the original `reply_path` or carry a fresh one; the merchant SHOULD
  accept a response over any `reply_path` it constructed for that notification
  while it remains unacknowledged.
- MUST discard a response that does not arrive on a `reply_path` it constructed
  for a notification still awaiting acknowledgement, or whose echoed
  `payment_hash` does not match that notification.

The PoS:

- MUST send its response, if any, over the notification's `reply_path`; it has
  no other means of replying. It MAY drop a `reply_path` whose `first_node_id`
  it cannot reach.
- SHOULD still process a `payment_notification` that arrives without a
  `reply_path` — the payment may be genuine — but it has no way to respond, so
  a merchant that omits the `reply_path` will exhaust its retries and escalate
  to manual reconciliation.
- MUST NOT respond at all to a notification whose signature does not verify
  (see [`payment_notification`](#payment_notification)).
- SHOULD answer, ack or nack, a notification whose signature verifies.
- MUST NOT suppress its first response for a given (order, payment hash) whose
  checks pass, an unreachable `reply_path` excepted. It MAY rate-limit repeats
  of a response it has already sent.
- SHOULD answer `unknown_order` at least once per arrival path.
- SHOULD rate-limit signature verification itself.

#### Rationale

##### Correlation

Responses are as unauthenticated as notifications are: onion messages carry no
sender authentication, and the merchant's `offer_paths` are in the template,
which may be public. An `ack` the merchant wrongly attributes to a pending
notification silences the retry loop for a payment that never reached the PoS;
a forged `nack` flags a genuinely paid order for manual reconciliation.

The merchant's node id is public, so anyone can build a blinded path to it and
choose the recipient data; a guessable identifier lets a third party produce an
`ack` the merchant accepts, silencing the retry loop for a payment the PoS
never learned about. Echoing the payment hash means correlation does not rest
on the path alone.

##### Response policy

The response policy turns on whether the signature verified, because that is
what divides messages the merchant provably sent from messages anyone could
have sent. A notification whose signature does not verify is unattributable, so
there is nobody to inform, and answering makes the PoS a reflector and an
order-state oracle. A notification whose signature verifies came from the
merchant; the responses are what the merchant needs, and withholding them
drives a correctly settled payment to manual reconciliation.

Rate-limiting repeats is permitted because onion messages have no replay
protection: a hop that captured a passing notification can replay it verbatim,
and an unconditional response obligation would make the PoS an unbounded
reflector. Signature verification itself is rate-limited because each forged
notification costs a BIP340 verification, and a PoS is typically a small
device.

(Hop-level rate limiting can still drop the genuine notification itself; that
is a liveness risk the merchant's retry-and-escalate behavior covers.)

##### `unknown_order`

`unknown_order` needs care: it is decided before any verification key is
available, since the key comes from the order the arrival path identifies. It
is therefore the only reason code an unauthenticated party can elicit. The PoS
SHOULD answer it at least once per arrival path, because a genuine state loss
is what the merchant needs to hear about and it is the one nack the merchant
retries. That is safe only when the PoS can tell a path it built from a path an
attacker built — which is what the unguessability requirement in [Notification
Path](#notification-path) provides, and why the keyed-PRF or MAC form is
preferred: after a state loss, a bare random value looked up in a table that no
longer exists is indistinguishable from a forgery, so the PoS cannot answer
honestly without also answering every probe.

### `payment_proof`

The customer MAY send a `payment_proof` onion message to the PoS via the
notification path. This sender-side extension provides redundancy (if the
merchant's notification fails) and prevents the merchant from denying payment.
The PoS never sees the invoice, so the proof is what lets it verify the payment
independently of the merchant.

The proof payload is a BOLT 12 payer proof as defined in
[bolts#1295](https://github.com/lightning/bolts/pull/1295): a redacted copy of
the invoice TLV stream that carries the invoice node's `signature`, the
`proof_preimage`, and a `proof_signature` from the customer's `invreq_payer_id`.

#### Requirements

A customer sending a `payment_proof`:

- MUST NOT redact the invoice `payment_token` or `invoice_amount` TLVs from the
  proof; a proof missing either cannot be checked and will be rejected. Note
  that `payment_token` has a type number defined by this bLIP, so a wallet
  implementing only bolts#1295 may treat it as unknown.

A reader of `payment_proof` (the PoS):

- MUST accept a `payment_proof` only if:
  - The payer proof is valid per the reader requirements of bolts#1295
  - The proof arrived on a notification path the PoS constructed, identifying
    an order via the path's `order_metadata`
  - `invoice_node_id` matches the `offer_issuer_id` of the template that
    order's offer was built from — not merely some template the PoS knows
  - The proof discloses the invoice `payment_token` TLV, and it is byte-for-byte
    identical to the `payment_token` ciphertext the PoS sealed into the offer
    for that order. A proof disclosing no `payment_token` MUST be rejected.
  - `invoice_amount` is included and is at least that order's expected amount

An accepted proof marks the order paid, exactly as a passing notification does:
a `payment_notification` subsequently arriving for that order is re-acked under
the already-paid rule in [`payment_notification`](#payment_notification). The
same expiry treatment applies as for notifications.

#### Rationale

##### Order binding

The ciphertext equality check binds the proof to the order it arrives for, and
it is the same binding a `payment_notification` gets from `payment_token_hash`
— one compares the ciphertext, the other its hash. It works because
`order_metadata` is fresh per order and is sealed inside the token, so no two
orders share a `payment_token` ciphertext. A valid proof for one order
therefore cannot confirm another: paying a cheap order A and replaying its
proof down order B's notification path fails, because the proof discloses order
A's token rather than the one sealed for B. Note that this is why
`order_metadata` remains in `sealed_order` even though it no longer
authenticates anything — without it, two orders sharing an amount and
description would share a ciphertext, and the check would confirm the wrong
order. The PoS compares against the ciphertext it produced at offer
construction, so the check requires no decryption.

##### Key binding

Binding `invoice_node_id` to the order's own template matters for the same
reason the notification's signature is verified against that template's key: a
PoS serving several merchants (or holding a rotated template) would otherwise
accept a proof signed by a *different* merchant's node over an invoice that
embeds this order's ciphertext.

##### The chain

The proof cannot pin the payment's chain: the proof is a redacted TLV stream and
the payer chooses what to redact, so a check on a disclosed `invreq_chain` would
be voluntary. The denomination instead rests on the merchant's `invoice_request`
checks (see [Invoice Requests](#invoice-requests)) — a merchant-signed invoice
embedding the order's token exists only if those checks passed, and a merchant
that missigns is already outside the [Security Model](#security-model).

## Rationale

### Why Sign the Notification?

An earlier form of this protocol authenticated the notification with a shared
secret: the PoS sealed `order_metadata` into the `payment_token`, the merchant
decrypted it and relayed it, and the PoS accepted the notification if the relayed
value matched. That works, but it makes the secret's confidentiality a protocol
obligation on every party that touches it, and it puts the merchant in the
position of decrypting a secret on demand for anyone who sends an
`invoice_request`.

Signing removes all of that. The PoS already knows the merchant's
`offer_issuer_id` from the template — it is the key the merchant signs invoices
with, and the key the PoS encrypts the token to. Using it to sign the notification
costs nothing new: the construction is BOLT 12's own, parameterized over the
stream name, so implementations already have the code.

The signature needs its own tag rather than reusing the invoice's, because anyone
can obtain a merchant-signed *invoice* for free by sending an `invoice_request`
and never paying. A shared tag would hand out valid notification signatures.

What signing does not do is make the notification self-sufficient. A signature
proves the merchant sent it, not which order it concerns, so the notification must
still name the order — which it does by committing to the `payment_token`
ciphertext. And `order_metadata` remains necessary for two jobs that the signature
never touched: recognising the arrival path as one the PoS built (see [Notification
Path](#notification-path)), and keeping each order's token ciphertext distinct (see
[`payment_proof`](#payment_proof)).

### Why Not LNURL/LUD-21?

LNURL with LUD-21 requires a centralized callback server, does not provide
proof-of-payer, and introduces privacy trade-offs. This protocol is fully
decentralized and builds on BOLT 12's existing infrastructure.

## Open Questions

1. **Proof of payment**: Resolved by adopting BOLT 12 payer proofs
   ([bolts#1295](https://github.com/lightning/bolts/pull/1295)) for the
   [payment proof](#payment_proof), which bind the preimage to the
   merchant-signed invoice and add proof of payer via `proof_signature`. It

   support payer proofs.

2. **Async payments**: Offline merchants cannot receive payments or send
   notifications. Deferred.

3. **Authenticating the invoice request to the merchant**: the merchant cannot
   tell a PoS-issued per-order offer from one any template holder sealed itself
   (see [Security Model](#security-model)). BOLT 12 reserves `offer_metadata`
   for exactly this — an authentication cookie over the other offer fields — so
   the PoS could MAC the per-order fields under a key shared at template
   hand-off, and the merchant could reject requests that fail to verify. This
   would also let the merchant reject expired orders, which are likewise
   unauthenticated today.

   This is the most consequential of the open questions. It is the only mechanism
   that would let a merchant refuse to invoice, and sign a notification for, an
   offer it has no reason to believe came from its own terminal. Everything the
   merchant checks about a `payment_token` today compares one attacker-supplied
   value against another. The PoS-side `payment_token_hash` check keeps that gap
   from costing anyone their goods, but it cannot keep the merchant from settling
   payments for orders that never existed.
