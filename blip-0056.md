## Abstract

This bLIP defines a protocol for point-of-sale (PoS) terminals to receive
payment notifications from merchants using BOLT 12 offers and onion messages.
The PoS never touches customer funds and is not on the payment path. The
merchant delegates offer creation to the PoS, which constructs offers containing
notification blinded paths back to itself. When the merchant receives payment,
it notifies the PoS via onion message.

## Motivation

A merchant wants to accept Lightning payments through a point-of-sale device
(e.g., a physical terminal or web checkout). The PoS must not touch customer
funds: the customer pays the merchant directly, and the PoS has no payment
channels.

The PoS needs to:

- Present an order for the customer to pay
- Display confirmation when the merchant has been paid
- Record payment for accounting and tax purposes

Existing solutions like LNURL with LUD-21 webhooks require centralized callback
servers and introduce trust and privacy trade-offs. This proposal provides a
decentralized alternative built on BOLT 12 and onion messages.

## Specification

### Actors

- **Customer**: Standard BOLT 12 wallet. No sender-side modifications required
  for the base flow. The optional `payment_proof` (Step 7) requires wallet
  support for BOLT 12 payer proofs
  ([bolts#1295](https://github.com/lightning/bolts/pull/1295)).
- **Point-of-Sale (PoS)**: Lightning node without payment channels. Unannounced,
  communicates via onion messages only.
- **Merchant**: Always-online Lightning node with channel liquidity. Must
  support this notification protocol.

### Setup Phase: Offer Template

The merchant creates an **offer template** and provides it to the PoS:

- Amountless, no description (filled per-order by the PoS)
- Contains blinded paths to the merchant for invoice requests

The template carries the `payment_notifications` feature bit to signal to the
PoS that the merchant supports the protocol.

The offer template MAY be refreshed periodically by the merchant to rotate
blinded paths.

### Feature Bit

A new feature bit is defined for `offer_features`:

| Bit  | Name                     | Description |
|------|--------------------------|-------------|
| TBD  | `payment_notifications`  | The merchant supports this protocol and will deliver a `payment_notification` for per-order offers carrying a `notification_path` and `payment_token` |

The merchant sets this bit on the offer template to advertise support. The PoS
MUST NOT use a template that does not set it, and the bit remains set on each
per-order offer the PoS constructs. The merchant reads it from the mirrored
`invoice_request`: it embeds the `notification_path` and the decrypted
`order_id` in the invoice's `path_id` and delivers a `payment_notification` at
payment time.

A single bit covers both new offer fields since they are only useful together:
the `payment_token` authenticates the notification (see [Authentication and
Forgery Prevention](#authentication-and-forgery-prevention)), so an offer
carrying a `notification_path` MUST also carry a `payment_token`. If the
mirrored offer sets `payment_notifications` but either field is missing, the
`payment_token` fails to decrypt, or the token's `amount` or `description` does
not match the offer, the merchant MUST reject the `invoice_request` instead of
issuing an invoice it cannot deliver a notification for.

### Per-Order Offer Construction

For each order, the PoS constructs a complete offer from the template by adding:

1. **Amount**: the order total, denominated in millisatoshis
   (`offer_currency`-denominated offers are out of scope for this protocol)
2. **Description**: human-readable order description (optional)
3. **Expiry**: an `offer_absolute_expiry` bounding the order's lifetime
   (RECOMMENDED)
4. **`notification_path`**: one or more blinded paths back to the PoS
5. **`payment_token`**: the order fields `(amount, description, order_id)`
   sealed to the merchant, constructed as defined in [Payment Token
   Construction](#payment-token-construction)

The `payment_notifications` feature bit is inherited from the template and
remains set. The PoS presents this offer to the customer as a QR code or over
any other transport the PoS supports (e.g., NFC, BLE). The blinded paths and the
token ciphertext make the offer noticeably larger, so deployments using QR codes
SHOULD limit the offer to a single notification path.

The PoS stores the order data (including `order_id`) in the notification path's
message context, which only the PoS can read, and the order fields `(amount,
description, order_id)` in the `payment_token`, which only the merchant can
read. The merchant relays `order_id` in its notification, and the PoS matches it
against the `order_id` recovered from the path's message context. This is how
the PoS authenticates the merchant's notification.

#### Notification Path

The `notification_path` is a standard onion message blinded path to the PoS,
constructed per-order. It MUST NOT be part of the offer template.

The path's **message context** carries:

- `order_id` (the per-order secret also sealed in the `payment_token`)
- Expected payment amount
- Order description if present
- Any additional PoS-private verification data

This context is encrypted during blinded path construction and can only be
decrypted by the PoS. The PoS uses it to match the `order_id` relayed in the
notification when one arrives. The merchant treats the notification path as
opaque data throughout the protocol.

#### Payment Token Construction

When the PoS adds a `payment_token` TLV to the per-order offer, the token seals
the order fields, encrypted to a merchant public key:

```
payment_token = Enc(merchant_key, amount | description | order_id)
```

where `order_id` is the per-order secret generated by the PoS (see the entropy
requirements in [Per-Order Offer Construction](#per-order-offer-construction)).
Since the merchant parses the plaintext, the field encoding is part of the wire
format: fields MUST be [tlv encoded](https://github.com/lightning/bolts/blob/master/01-messaging.md#type-length-value-format).

- The token is encrypted to a merchant public key. The derivation of this key is
  left to the implementation; the merchant only needs to be able to decrypt the
  token at invoice-request time. The choice of encryption scheme is an open
  question (see [Open Questions](#open-questions)).
- At invoice-request time the merchant decrypts the token and MUST verify that
  its `amount` and `description` match the mirrored offer fields, rejecting the
  `invoice_request` on mismatch or decryption failure (see [Feature
  Bit](#feature-bit)). This catches simple tampering with the offer's cleartext
  fields before any payment happens. It is only a sanity check, however:
  encryption to the merchant key does not authenticate the sender, and a
  customer that can derive the key can construct a token matching a tampered
  offer. The PoS still catches such a token through the `order_id` check. The
  merchant records `order_id` for relay in the notification.

The merchant cannot read the notification path's message context, which is
sealed to the PoS, so the token is its only source of order data. When the
notification arrives, the PoS accepts it only if the relayed `order_id` matches
the one in the path's message context. The customer never sees the relayed
`order_id`: it travels inside an onion message encrypted to the PoS.

### Payment Flow

```
Customer                    Merchant                    PoS
   |                           |                         |
   |  1. scan offer QR code from PoS  ----------------->|
   |                           |                         |
   |  2. invoice_request  ---> |                         |
   |     (via blinded path)    |                         |
   |                           |                         |
   |  3. <--- invoice          |                         |
   |     (with blinded         |                         |
   |      payment paths)       |                         |
   |                           |                         |
   |  4. payment ----------->  |                         |
   |     (via blinded          |                         |
   |      payment path)        |                         |
   |                           |                         |
   |                           |  5. payment_notification|
   |                           |  ---------------------->|
   |                           |     (via notification   |
   |                           |      blinded path)      |
   |                           |                         |
   |                           |  6. <-- notification_ack|
   |                           |                         |
   |  7. payment_proof  ---------------------->          |
   |     (optional, via                                  |
   |      notification path)                             |
   |                           |                         |
```

#### Steps 1-3: Invoice Request

The customer scans the QR code and sends an `invoice_request` to the merchant
via the offer's blinded path. The merchant:

1. Identifies the offer as one of its own templates (mechanism is
   implementation-specific; see [Template Offer
   Identification](#template-offer-identification))
2. Recovers the signing key for the template (e.g., re-derived from a nonce, or
   stored)
3. If the mirrored offer sets `payment_notifications`, decrypts the
   `payment_token` and verifies its `amount` and `description` against the
   mirrored offer fields, rejecting the `invoice_request` if the token or
   `notification_path` is missing, the token fails to decrypt, or the fields do
   not match (see [Feature Bit](#feature-bit))

#### Step 4: Payment

The customer pays the invoice via the blinded payment paths. Standard BOLT 12,
no sender-side modifications required.

#### Step 5: Payment Notification

When the merchant claims the payment, it:

1. Extracts the `notification_path` and the `order_id` from the `path_id`
   (recovered from the blinded payment path's `encrypted_data_tlv`)
2. Sends a `payment_notification` onion message containing `payment_hash`,
   `preimage`, `amount_msat`, and the `order_id` recovered from the
   `payment_token`
3. Includes a reply path for acknowledgement
4. Retries with backoff until `notification_ack` or `notification_nack` is
   received (onion messages are best-effort), alternating among the notification
   paths when more than one was provided. Retries SHOULD stop once the offer's
   `offer_absolute_expiry` plus a grace period has passed. The merchant SHOULD
   report undeliverable notifications to its operator, since it then holds a
   payment the PoS never confirmed

#### Step 6: Acknowledgement

The PoS receives the `payment_notification` and:

1. Decrypts the order context from the notification path's message context,
   recovering `order_id`, the expected amount, and the description
2. Verifies the `order_id` relayed in the notification matches the one recovered
   from the message context (authenticates the notification as
   merchant-originated)
3. Verifies `amount_msat >= expected_amount`
4. Verifies that hashing the `preimage` produces the `payment_hash`
5. Sends `notification_ack` on success, `notification_nack` with a reason code
   otherwise
6. Displays payment confirmation to the customer

Step 2 is what authenticates the notification: without a matching `order_id` it
could have been forged by the customer, so `amount_msat` is only trusted once
the `order_id` matches.

The merchant retries until acknowledged, and an observer could replay a captured
onion packet, so the PoS MUST handle duplicates: a second notification for an
already-confirmed order is answered with `notification_ack` again without
recording the payment twice. Notifications for unknown or expired orders are
answered with `notification_nack`. The PoS SHOULD drop order state once the
order's expiry plus a grace period has passed.

#### Step 7: Optional Payment Proof

The customer MAY send a `payment_proof` onion message to the PoS via the
notification path. This sender-side extension provides redundancy (if the
merchant's notification fails) and prevents the merchant from denying payment.

The proof payload is a BOLT 12 payer proof as defined in
[bolts#1295](https://github.com/lightning/bolts/pull/1295): a redacted copy of
the invoice TLV stream that carries the invoice node's `signature`, the
`proof_preimage`, and a `proof_signature` from the customer's `invreq_payer_id`.
Omitted fields are replaced by the Merkle hashes needed to still validate the
invoice signature. A bare `(preimage, payment_hash)` pair would prove nothing
here, since the PoS never sees the invoice and any self-consistent pair passes a
hash check. The payer proof instead shows that a real invoice existed, was
signed by the merchant, and was paid by this customer, and the PoS can verify it
even when the merchant's notification never arrives.

The PoS accepts a `payment_proof` only if:

- The payer proof is valid per the reader requirements of bolts#1295, which
  include verifying that `SHA256(proof_preimage)` equals `invoice_payment_hash`,
  that `signature` validates against the reconstructed invoice Merkle root, and
  that `proof_signature` validates against `invreq_payer_id`
- `invoice_node_id` matches the merchant signing key the PoS knows from the
  offer template
- The mirrored `payment_token` TLV is included (not elided) in the proof and
  equals the token the PoS issued for this order. The token ciphertext is unique
  per order, so this binds the proof to the order and prevents replaying a proof
  of a different equal-amount payment to the same merchant
- `invoice_amount` is included and is at least the expected order amount

The `proof_signature` also gives the PoS proof of payer, which the merchant's
notification does not provide and which is useful for receipts and refunds.

### New TLV Fields

#### Offer TLVs

| Type | Name | Description |
|------|------|-------------|
| TBD (odd)  | `notification_path` | Blinded onion message path(s) to the PoS. Order context is carried in the path's message context. |
| TBD (odd)  | `payment_token` | Order fields `(amount \| description \| order_id)` encrypted to a merchant-recoverable key; the merchant verifies `amount`/`description` against the offer and relays `order_id` in the notification (see [Payment Token Construction](#payment-token-construction)). |

Both types MUST be assigned odd TLV type numbers within the mirrored offer
range. Existing wallets ignore unknown odd fields and mirror them verbatim into
the `invoice_request`; an even type number would make every existing wallet
reject the offer, breaking the goal of working with unmodified senders.

Since BOLT 12 mirrors offer fields into the `invoice_request`, the merchant can
read these TLVs at invoice-request time: it embeds the `notification_path` and
the decrypted `order_id` in the blinded payment path's `path_id` for retrieval
when the payment is claimed.

#### Onion Message TLVs

| Type | Name | Description |
|------|------|-------------|
| TBD  | `payment_notification` | Notification from merchant to PoS (see payload below) |
| TBD  | `notification_ack` | Positive acknowledgement from PoS |
| TBD  | `notification_nack` | Negative acknowledgement from PoS, carrying a reason code |
| TBD  | `payment_proof` | Optional BOLT 12 payer proof ([bolts#1295](https://github.com/lightning/bolts/pull/1295)) from customer to PoS (see Step 7) |

A `notification_nack` carries a one-byte reason code so the merchant can tell
recoverable failures from terminal ones: `unknown_order` (no matching order
state), `order_expired`, `order_id_mismatch` (possible forgery or corrupted
token), `amount_insufficient`. A merchant receiving a nack has already claimed
the payment; it SHOULD report the failure to its operator for manual
reconciliation rather than retry.

#### Notification Payload

| Field | Type | Description |
|-------|------|-------------|
| `payment_hash` | 32 bytes | Payment hash from the invoice |
| `preimage` | 32 bytes | Payment preimage released by the merchant |
| `amount_msat` | u64 | Amount paid in millisatoshis |
| `order_id` | 16+ bytes | Per-order secret recovered from the `payment_token` and relayed by the merchant |

The `order_id` is the secret the PoS sealed into the `payment_token` for this
order. Only the merchant can decrypt the token, so relaying the correct
`order_id` authenticates the notification and ties it to the order. The customer
never sees the relayed value, since the notification travels inside an onion
message encrypted to the PoS. The PoS matches it against the `order_id` in the
notification path's message context.

### Authentication and Forgery Prevention

**Forged notification**: The customer knows the `notification_path` (it is in
the offer) and can send onion messages over it. A `preimage` that hashes to the
`payment_hash` is not sufficient evidence on its own: the customer can take a
valid `(preimage, payment_hash)` pair from any payment they made to the merchant
and assert an arbitrary `amount_msat` in a notification they send themselves,
confirming an expensive order for the price of a cheap one.

The `payment_token` prevents this. The PoS seals the order fields `(amount,
description, order_id)` to the merchant, where `order_id` is never reveled to the customer.
Only the merchant can decrypt the token, and the customer has
no way to learn `order_id`: the token ciphertext is opaque, and the notification
that relays it travels over an onion message encrypted to the PoS. The PoS
accepts a notification only if the relayed `order_id` matches the one in the
notification path's message context, which shows the notification came from the
merchant after claiming this order's payment. Without a matching `order_id` the
PoS does not trust `amount_msat`. This is why `payment_token` is required
whenever `payment_notifications` is used.

**Amount tampering**: A customer could lower the offer amount before sending the
invoice request and pay less. If the customer edits the cleartext fields without
touching the token, the merchant notices the mismatch with the token's sealed
`amount` and `description` and rejects the request before payment. The token is
encrypted rather than signed, though, so a customer that can derive the merchant
key can build a token matching the tampered amount, or copy a complete field set
from another order of the same PoS. Both get past the merchant but not past the
PoS: neither token contains the `order_id` sealed in this order's notification
path context, so the notification is answered with an `order_id_mismatch` nack.
The PoS also compares the notified `amount_msat` against the expected amount
from the path context and nacks on a shortfall. In these cases the payment has
already happened; the PoS refuses to confirm the order and the merchant has to
reconcile manually.

### Trust Model

The protocol authenticates notifications against a malicious customer; it does
not protect the PoS against the merchant node. The PoS trusts the merchant for
the truthfulness of `amount_msat` and for the notification being sent at all:
the merchant can decrypt any token, so a malicious or compromised merchant node
can fabricate a valid notification for an unpaid order, report a wrong amount,
or stay silent. This is acceptable when the merchant node is operated by or for
the same business as the PoS, which is the intended deployment. Where the
merchant node is a third-party host, that trust transfers to the operator. The
optional `payment_proof` protects against the merchant denying a payment, not
against fabrication.

The offer template is also not secret, in particular when published via BIP 353,
so any third party holding it can construct valid per-order offers that the
merchant will service, including encrypting a `payment_token` to the merchant
key. Funds always flow to the merchant, so there is no direct theft, but the
merchant cannot distinguish authorized PoS devices from arbitrary template
holders (e.g., a fake storefront directing victims to pay the real merchant).
Merchants that need to restrict which devices act as a PoS must provision the
token-encryption key out of band, at the cost of reintroducing a setup-time
secret.

### Privacy and Denial of Service

The `notification_path`'s introduction node is visible in every per-order offer.
A channel-less PoS builds its paths through its always-connected onion-message
peers, so all of a shop's orders will tend to share an introduction node, and
any customer or QR scraper can link them. Using more than one candidate
introduction node, where available, reduces this fingerprint. For the same
reason the `payment_token` encryption scheme should produce ciphertexts that
cannot be linked to the merchant key across offers (see [Open
Questions](#open-questions)).

Since the notification path is public, anyone holding the offer can spam onion
messages at the PoS. Verification is cheap (one context decryption and one
`order_id` comparison) and messages failing it are dropped without any state
change. The PoS and its onion-message peer SHOULD also rate-limit inbound
messages.

### Template Offer Identification

Key derivation is implementation-specific. The merchant identifies a template as
its own by the PoS delegation key, not by the feature bit: the
`payment_notifications` bit only advertises support and is present on every
offer derived from the template. The template MAY be distributed to the PoS out
of band, or published via a BIP 353 address (e.g., `vincenzo@hedwig.sh`) for
easy PoS configuration (see the template-publication caveat in [Trust
Model](#trust-model)).

Before using a template, the PoS MUST check that the `payment_notifications`
feature bit is set and that the fields it intends to fill (amount, description,
`notification_path`, `payment_token`) are unset.

## Rationale

### Why Not LNURL/LUD-21?

LNURL with LUD-21 requires a centralized callback server, does not provide
proof-of-payer, and introduces privacy trade-offs. This protocol is fully
decentralized and builds on BOLT 12's existing infrastructure.

## Backwards Compatibility

The base flow (Steps 1-6) requires no sender-side changes. Any BOLT 12 wallet
works, provided the new offer TLVs are assigned odd type numbers (see [New TLV
Fields](#new-tlv-fields)). The optional `payment_proof` (Step 7) requires
customer wallet support for BOLT 12 payer proofs
([bolts#1295](https://github.com/lightning/bolts/pull/1295)).

Merchant-side changes:

- Create and manage offer templates
- Recognize template offers and recover the appropriate signing key
- Embed notification paths in the blinded payment path's `path_id`
- Decrypt the `payment_token`, verify its `amount`/`description` against the
  mirrored offer, and relay `order_id` in the notification when
  `payment_notifications` is set; reject invoice requests where the token is
  missing, fails to decrypt, or does not match the offer
- Send notifications via onion messages at payment time, with bounded retries

PoS requirements:

- Construct offers from templates
- Generate a high-entropy per-order secret `order_id`, seal it (with the order
  fields) in the notification path's message context, and seal `(amount,
  description, order_id)` in the encrypted `payment_token`
- Authenticate incoming notifications by matching the relayed `order_id` against
  the path's message context, handle duplicates idempotently, and expire order
  state; then handle `payment_notification` and `payment_proof` messages

## Open Questions

1. **Proof of payment**: Resolved by adopting BOLT 12 payer proofs
   ([bolts#1295](https://github.com/lightning/bolts/pull/1295)) for Step 7,
   which bind the preimage to the merchant-signed invoice and add proof of payer
   via `proof_signature`. It remains open whether the merchant should also be
   able to forward a payer-proof-like attestation directly, for customers whose
   wallets do not support payer proofs.

2. **Async payments**: Offline merchants cannot receive payments or send
   notifications. Deferred.

3. **`payment_token` key derivation**: How the merchant derives/recovers the key
   used to encrypt the `payment_token` is intentionally left to the
   implementation; interop only requires that the PoS encrypts to a key the
   merchant can decrypt.

4. **`payment_token` encryption scheme**: The concrete scheme is not yet
   chosen. Desired properties: authenticated encryption, so that a corrupted
   token fails to decrypt rather than yielding garbage fields, and per-order
   unlinkability, so that ciphertexts cannot be linked to the merchant key
   across offers (e.g., ECIES with a fresh ephemeral key per token). Whether
   these are requirements or recommendations is open, and the scheme must be
   agreed for cross-implementation interop.
