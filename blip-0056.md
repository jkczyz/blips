## Abstract

This bLIP defines a protocol for point-of-sale (PoS) terminals to receive
payment notifications from merchants using BOLT 12 offers and onion messages.
The PoS never touches customer funds and is not on the payment path. The
merchant delegates offer creation to the PoS, which constructs offers containing
notification blinded paths back to itself. When the merchant receives payment,
it notifies the PoS via onion message. An optional `payment_proof` lets the
customer attest the payment directly to the PoS as a fallback.

## Motivation

A merchant wants to accept Lightning payments through a point-of-sale device
(e.g., a physical terminal or web checkout). The PoS must not touch customer
funds: the customer pays the merchant directly, and the PoS has no payment
channels.

The PoS needs to:

- Present an order for the customer to pay
- Display confirmation when the merchant has been paid
- Record payment for accounting and tax purposes

Existing solutions like LNURL with LUD-21 webhooks require centralized callback
servers and introduce trust and privacy trade-offs. This proposal provides a
decentralized alternative built on BOLT 12 and onion messages.

## Specification

### Actors

- **Customer**: Standard BOLT 12 wallet. No sender-side modifications required
  for the base flow. The optional [payment proof](#payment-proof) requires
  wallet support for BOLT 12 payer proofs
  ([bolts#1295](https://github.com/lightning/bolts/pull/1295)).
- **Point-of-Sale (PoS)**: Lightning node without payment channels. Unannounced,
  communicates via onion messages only. It never sees the invoice and is not on
  the payment path.
- **Merchant**: Always-online Lightning node with channel liquidity. Must
  support this notification protocol.


### Terminology

The following terms are used throughout the specification and are
defined in detail in the sections that follow:

| Term | Brief description |
|------|-------------------|
| `order_metadata` | Unpredictable per-order secret generated by the PoS; carried in the `notification_path` recipient data and sealed in the `payment_token` ([Notification Path](#notification-path)) |
| `notification_path` | Blinded onion message path(s) to the PoS, carrying `order_metadata` in the path's recipient data ([Notification Path](#notification-path)) |
| `payment_token` | `amount`, `description`, `notification_path_hash` and `order_metadata`, encrypted to the merchant; the merchant checks them and relays the decrypted plaintext in the notification, while the ciphertext is copied into the invoice for payer proofs ([Payment Token Construction](#payment-token-construction)) |
| `payment_notification` | Onion message from the merchant to the PoS at payment time ([New TLV Fields](#new-tlv-fields)) |
| `notification_ack` / `notification_nack` | PoS response confirming or rejecting the notification, sent over the notification's `reply_path` ([Reply Path](#reply-path)) |
| `payment_proof` | Optional BOLT 12 payer proof sent directly by the customer as a fallback ([Payment Proof](#payment-proof)) |

### Payment Flow

```
Customer                    Merchant                    PoS
   |                           |                         |
   |  1. scan offer QR code from PoS  ------------------>|
   |                           |                         |
   |  2. invoice_request  ---> |                         |
   |     (via blinded path)    |                         |
   |                           |                         |
   |  3. <--- invoice          |                         |
   |     (with blinded         |                         |
   |      payment paths)       |                         |
   |                           |                         |
   |  4. payment ----------->  |                         |
   |     (via blinded          |                         |
   |      payment path)        |                         |
   |                           |                         |
   |                           |  5. payment_notification|
   |                           |  ---------------------->|
   |                           |     (via notification   |
   |                           |      blinded path)      |
   |                           |                         |
   |                           |  6. notification_ack    |
   |                           |  <----------------------|
   |                           |     (via reply path)    |
   |                           |                         |
   |  7. payment_proof  ---------------------->          |
   |     (optional, via        |                         |
   |      notification path)   |                         |
   |                           |                         |
```

1. **Invoice request**: The PoS has already added `payment_token` and
   `notification_path` to the per-order offer. The customer scans it and
   sends a standard `invoice_request` via the offer's blinded path. The
   merchant identifies the template and applies the checks in [Merchant
   Requirements](#merchant-requirements): binding the notification path is
   security-critical and has no backstop at the PoS, while the amount and
   description comparisons are consistency checks that do not authenticate the
   requester. It then issues an invoice carrying the same `payment_token`
   ciphertext.

2. **Payment**: The customer pays the invoice via the blinded payment paths.
   Standard BOLT 12, no sender-side modifications required.

3. **Notification**: When the merchant claims the payment, it sends a
   `payment_notification` onion message to the PoS via the `notification_path`,
   including a `reply_path` for the response (see [Reply Path](#reply-path)).
   The merchant retries with backoff until acknowledged, up to an
   implementation-defined limit; if retries are exhausted without a response, it
   SHOULD escalate to manual reconciliation. (See [Notification
   Payload](#notification-payload).)

4. **Acknowledgement**: The PoS authenticates the notification by matching the
   relayed `payment_token` plaintext, `order_metadata` included, against what it
   sealed for the order that owns the arrival path, and answers over the
   notification's `reply_path` with `notification_ack` or `notification_nack`
   (or, for a notification that fails the checks, not at all).

5. **Optional payment proof**: The customer MAY send a `payment_proof` directly
   to the PoS as a fallback. (See [Payment Proof](#payment-proof).)

### Setup Phase: Offer Template

The merchant creates an **offer template** and provides it to the PoS:

- Amountless, no description (filled per-order by the PoS)
- Contains blinded paths to the merchant for invoice requests
- MUST include `offer_issuer_id` (the merchant's offer signing key)
- MUST NOT set `offer_chains`, `offer_currency`, or `offer_quantity_max`: the
  merchant's own checks (see [Merchant
  Requirements](#merchant-requirements)) reject per-order offers carrying any
  of these, so a template setting them yields offers the merchant itself
  refuses. A merchant that accepts non-bitcoin chains elsewhere must publish a
  separate, bitcoin-only template for PoS use.

The PoS MUST NOT use a template that violates these constraints.

The template carries the `payment_notifications` feature bit to signal to the
PoS that the merchant supports the protocol.

The offer template MAY be refreshed periodically by the merchant to rotate
blinded paths.

The template MAY be published via a BIP 353 address (e.g., `vincenzo@hedwig.sh`) that
resolves to it. With a BIP 353 address the PoS can be configured once: it resolves
the address to obtain a fresh template whenever it needs one, and the merchant
(or its wallet vendor) keeps the resolved offer up to date with fresh blinded paths.
The merchant still has to refresh those paths, but the PoS doesn't need to be
re-configured each time.

### Per-Order Offer Construction

For each order, the PoS constructs a complete offer from the template by adding:

1. **Amount**: the order total, denominated in millisatoshis. So that the order
   total is exactly the amount sealed in the `payment_token`, the PoS MUST NOT
   set `offer_currency` (currency-denominated offers are out of scope), MUST NOT
   set `offer_quantity_max`, and MUST NOT set `offer_chains` (per-order offers
   are bitcoin-only, and BOLT 12 takes an absent `offer_chains` to mean
   bitcoin).
2. **Description**: human-readable order description (REQUIRED; BOLT 12
   requires `offer_description` for amount-bearing offers)
3. **Expiry**: an `offer_absolute_expiry` bounding the order's lifetime
   (RECOMMENDED)
4. **`notification_path`**: one or more blinded paths back to the PoS
5. **`payment_token`**: the order fields and `order_metadata` encrypted to the
   template's `offer_issuer_id`, constructed as defined in [Payment Token
   Construction](#payment-token-construction)

The `payment_notifications` feature bit is inherited from the template and
remains set. The PoS presents this offer to the customer as a QR code or over
any other transport the PoS supports (e.g., NFC, BLE). The blinded paths and the
token ciphertext make the offer noticeably larger, so deployments using QR codes
SHOULD limit the offer to a single notification path.

The PoS MUST retain, per order: the `order_metadata`, the sealed `payment_token`
plaintext, the `payment_token` ciphertext it placed in the offer, the expected
amount, the order's expiry (if any), the `offer_issuer_id` of the template the
order was built from, and — once the order is paid — the `payment_hash` of the
payment that settled it. Every check the PoS performs on a notification or a
payment proof compares against this state; the ciphertext in particular cannot
be re-derived if `Enc` is randomized. State MUST be retained for an
implementation-defined period after the order settles or expires, rather than
discarded immediately, so that a retried notification for an order already paid
can be re-acked and a late one can be answered `order_expired` rather than
`unknown_order`.

#### Notification Path

The `notification_path` is a standard onion message blinded path to the PoS,
constructed per-order. It MUST NOT be part of the offer template, and it MUST be
used only for its intended purpose: receiving `payment_notification` and
`payment_proof` messages for this one order.

The path's recipient data — the data the PoS encrypts to itself when it builds
the blinded path — carries `order_metadata`: an opaque `byte..` sequence defined
by the PoS. This data is encrypted during blinded path construction and can only
be decrypted by the PoS. The PoS uses it to correlate an incoming notification
to the correct order and to authenticate the notification. The path's recipient
data is opaque to the merchant — it never learns `order_metadata` from the path
— though the merchant does parse the `notification_path` value into blinded
paths, hash it verbatim, and select a path to send over (see [Merchant
Requirements](#merchant-requirements)).

`order_metadata` is the sole authenticator of a payment notification (see
[Authentication and Forgery
Prevention](#authentication-and-forgery-prevention)), so its construction is
normative:

- `order_metadata` MUST contain at least 16 bytes (128 bits) of entropy that is
  unguessable to any other party: fresh output of a cryptographically secure
  random number generator, or an equally long output of a keyed pseudorandom
  function (such as HMAC) over an order identifier, keyed with a secret known
  only to the PoS.
- The PoS MUST NOT compute that component from values known to or predictable by
  the customer — order sequence numbers, timestamps, amounts, descriptions —
  without mixing in a secret known only to the PoS. A bare hash or encoding of
  such values is not acceptable; what makes the keyed-PRF construction above
  safe is the key, not the input.
- The PoS MUST generate a fresh `order_metadata` for each order and MUST NOT
  reuse a value across orders. A PoS using the keyed-PRF construction MUST NOT
  reuse the order identifier across orders (e.g., a counter that survives
  restart, or a random nonce); the CSPRNG construction satisfies this
  requirement unconditionally.

Additional PoS-private fields (for example, order correlation or expected
amount) MAY be encoded alongside the unguessable component using an internal
format such as TLVs, and MUST NOT reduce its entropy; this bLIP does not define
the contents. The value is compared by exact byte equality, so any internal
structure is invisible to the protocol.

#### Payment Token Construction

When the PoS adds a `payment_token` TLV to the per-order offer, the token seals
the order's identity, encrypted to the template's `offer_issuer_id`:

```
payment_token = Enc(offer_issuer_id, sealed_order)
```

`sealed_order` contains:

- `amount`: the offer amount in millisatoshis
- `description`: the offer description
- `notification_path_hash`: SHA256 over the exact octets the PoS places in the
  `notification_path` TLV value of the same offer (the value only, not the type
  and length)
- `order_metadata`: the per-order secret

The plaintext inside `payment_token` MUST be
[tlv encoded](https://github.com/lightning/bolts/blob/master/01-messaging.md#type-length-value-format).
`Enc` MUST be an authenticated encryption scheme, so that a party who cannot
read the plaintext also cannot modify it: without ciphertext integrity a
tamperer could alter the sealed `amount` while leaving `order_metadata` intact.

The PoS MUST encrypt to the `offer_issuer_id` from the offer template. The
merchant MUST decrypt with the corresponding private key. This matches the
BOLT 12 rule that `invoice_node_id` equals `offer_issuer_id` when present, and
avoids encrypting to a last-hop `blinded_node_id` (which the PoS cannot know at
offer-construction time and which may differ across `offer_paths`).

`amount` and `description` are the cleartext offer fields the merchant verifies
against the invoice request. `notification_path_hash` binds the token to the
one path the notification may travel on. `order_metadata` is the same per-order
secret the PoS places in the `notification_path` recipient data; the merchant
decrypts the token, performs the checks below, and relays the decrypted
`payment_token` in the notification so the PoS can authenticate the payment.

Encrypting the token is what shares `order_metadata` with the merchant — and
only with the merchant. No other party ever sees it in cleartext, which is what
makes it usable as an authenticator (see [Authentication and Forgery
Prevention](#authentication-and-forgery-prevention)). Preserving that property
is normative: the merchant MUST NOT include the decrypted `sealed_order`, or
any part of `order_metadata`, in any message other than a `payment_notification`
sent over the bound `notification_path`. In particular it MUST NOT appear in an
`invoice_error`, in the invoice (which carries only the `payment_token`
ciphertext), in an operator-visible receipt reachable by the payer, or in any
other data reachable by a party other than the PoS.

The token carries no proof of origin: `offer_issuer_id` is a public key, so
anyone can seal a well-formed `payment_token` over fields of their choosing.
Checks on the token's contents are consistency checks, not authentication (see
[Authentication and Forgery
Prevention](#authentication-and-forgery-prevention)).

### Merchant Requirements

BOLT 12 requires an `invoice_request` reader to reject unless "the offer fields
do not exactly match a valid, unexpired offer". A merchant implementing this
bLIP cannot apply that rule to a per-order offer: the offer was built by the PoS
and the merchant has never seen it. The requirements below replace that check
for an `invoice_request` carrying a `payment_token`. Everything else BOLT 12
requires of an `invoice_request` reader still applies.

The merchant's view of a per-order offer is only what the `invoice_request`
carries, and the PoS-added offer fields are not signed by anyone. The merchant
therefore MUST reject an `invoice_request` carrying a `payment_token` unless all
of the following hold:

- `offer_issuer_id` is present and is one of the merchant's own issuer keys
  (this is how the merchant identifies the template), and the `payment_token`
  decrypts and authenticates under that key's private half
- `offer_amount` is present and equals the token's `amount`; `offer_description`
  is present and equals the token's `description`. Both comparisons are over the
  raw TLV value octets, with no normalization.
- `offer_currency` and `invreq_quantity` are absent (per-order offers are
  millisatoshi-denominated and single-item)
- `offer_chains` is absent, and `invreq_chain` is either absent or the bitcoin
  chain hash
- `notification_path` is present, parses as one or more non-empty
  `blinded_path`s, and hashes to the token's `notification_path_hash`. The
  merchant MUST hash the octets of the `notification_path` TLV value exactly as
  received, without parsing and re-serializing them.
- The amount the merchant would invoice (`invreq_amount` when present, otherwise
  `offer_amount`) is at least the token's `amount`

The merchant MUST also reject an `invoice_request` that carries a
`notification_path` without a `payment_token`, and MUST NOT send a
`payment_notification` for any `invoice_request` it rejected.

When issuing the invoice, the merchant MUST copy the `payment_token` TLV value
from the `invoice_request` byte-for-byte; it MUST NOT re-encode or re-seal it.
The payer proof's ciphertext-equality check (see [Payment
Proof](#payment-proof)) compares the invoice's copy against the ciphertext the
PoS sealed, so a re-sealed copy — even to the same plaintext, under a randomized
`Enc` — would fail every proof.

The merchant MUST send the `payment_notification` over a path contained in the
`notification_path` TLV value whose hash the token commits to, and MUST NOT send
it over any other path. It MAY use a different path from that value for each
retry, and SHOULD NOT send more than one copy at a time — not for secrecy (the
payload is onion-encrypted to the PoS on every path) but so that one
notification corresponds to one expected acknowledgement. It MUST relay the
decrypted plaintext verbatim, exactly as recovered from `Enc`, without parsing,
reordering, re-encoding, or dropping any record — the PoS compares it byte for
byte.

Because the hash covers the `notification_path` value byte for byte, any reader
that forwards the value MUST copy it unchanged. In particular it MUST NOT
re-encode a `blinded_path`'s `first_node_id` between the two forms
`sciddir_or_pubkey` permits. An unmodified BOLT 12 payer satisfies this, since
BOLT 12 requires it to copy all offer fields into the `invoice_request`
unchanged; the requirement matters for readers that understand
`notification_path` and might normalize it.

Without the `notification_path_hash` check the merchant is a confused deputy: it
would relay the decrypted `order_metadata` to whatever path the *customer* put
in the `invoice_request`. An attacker could pair a victim order's
`payment_token` with a path to its own node, pay a token amount, read
`order_metadata` out of the notification it receives, and then forge a fully
valid notification down the victim order's real path. Binding the path into the
token means the only paths the secret can ever travel on are the ones the PoS
built for that order. The amount and field checks close the same oracle via an
under-priced invoice. Pinning the denomination — no `offer_currency`, no
`offer_chains`, no non-bitcoin `invreq_chain` — keeps the amount comparison
well-defined: BOLT 12 computes the expected amount in the `invreq_chain`
currency, so a customer who requested a chain the merchant also supports could
otherwise pay the order total in another chain's units and still satisfy every
amount check here and at the PoS.

### New TLV Fields

#### Offer TLVs

| Type | Name | Description |
|------|------|-------------|
| TBD (odd)  | `notification_path` | Blinded onion message path(s) to the PoS. `order_metadata` is carried in the path's recipient data. |
| TBD (odd)  | `payment_token` | `amount`, `description`, `notification_path_hash` and `order_metadata` encrypted to the offer's `offer_issuer_id`; the merchant checks them against the invoice request and relays the decrypted plaintext in the notification (see [Payment Token Construction](#payment-token-construction)). |

#### Invoice TLVs

| Type | Name | Description |
|------|------|-------------|
| TBD (odd)  | `payment_token` | Copy of the offer `payment_token` ciphertext. The merchant MUST include this when issuing an invoice for a per-order offer that carries `payment_token`, so payer proofs can disclose it. |

#### Onion Message TLVs

| Type | Name | Description |
|------|------|-------------|
| TBD  | `payment_notification` | Notification from merchant to PoS (see payload below) |
| TBD  | `notification_ack` | Positive acknowledgement from PoS, echoing the notification's `payment_hash` |
| TBD  | `notification_nack` | Negative acknowledgement from PoS, echoing the notification's `payment_hash` and carrying a reason code |
| TBD  | `payment_proof` | Optional BOLT 12 payer proof ([bolts#1295](https://github.com/lightning/bolts/pull/1295)) from customer to PoS (see [Payment Proof](#payment-proof)) |

A `notification_nack` carries a one-byte reason code so the merchant's
reconciliation report can say why the notification was refused:

| Code | Name | Meaning |
|------|------|---------|
| 0 | `unknown_order` | No matching order state at the PoS |
| 1 | `order_expired` | The order is past its expiry |
| 2 | `token_mismatch` | Relayed plaintext did not match what the PoS sealed for the order that owns the arrival path (possible forgery or corrupted token) |
| 3 | `amount_insufficient` | Notified `amount_msat` is below the expected order amount |

A merchant receiving a nack has already claimed the payment; it SHOULD report
the failure to its operator for manual reconciliation rather than retry. The one
exception is `unknown_order`, which may mean the PoS lost its state (e.g. a
restart): the merchant MAY retry that one, and escalates if it recurs.

#### Notification Payload

The `payment_notification` TLV payload contains:

1. data:
   * [`sha256`:`payment_hash`]
     * The payment hash from the invoice
   * [`32*byte`:`preimage`]
     * The payment preimage released by the merchant
   * [`u16`:`payment_token_len`]
   * [`payment_token_len*byte`:`payment_token`]
     * The decrypted `payment_token` relayed by the merchant
   * [`tu64`:`amount_msat`]
     * Amount paid in millisatoshis

The `notification_ack` and `notification_nack` payloads contain:

1. data:
   * [`sha256`:`payment_hash`]
     * Echo of the notification's `payment_hash`, for correlation (see
       [Reply Path](#reply-path))

with `notification_nack` additionally containing:

2. data:
   * [`byte`:`reason`]
     * A reason code from the table above. A merchant receiving an
       unrecognized code treats it as a terminal failure.

The relayed `payment_token` is the decrypted contents of the token the PoS
sealed into the offer for this order. On receiving a notification, the PoS MUST
proceed as follows:

- Identify the order from the `order_metadata` in the **arrival path's**
  recipient data. A PoS MUST NOT identify the order from the relayed value:
  doing so drops the path-to-order binding, and a notification replayed down a
  different order's path would credit the original order again. If no order owns
  the arrival path, the reason code is `unknown_order`.
- If that order is already marked paid and the notification's `payment_hash`
  equals the one recorded for it, respond with `notification_ack` and stop —
  regardless of expiry, so that a lost or delayed acknowledgement does not
  escalate a correctly credited order to manual reconciliation. The PoS MUST
  credit an order at most once. If the order is paid but the `payment_hash`
  differs, run the plaintext and amount checks below (skipping expiry): if they
  pass, the customer paid twice — ack, but SHOULD flag the order for operator
  attention rather than absorb the second payment silently; if they fail, treat
  it as any other failing notification.
- If the order is past its expiry, the reason code is `order_expired`. The PoS
  SHOULD apply a grace period beyond `offer_absolute_expiry` covering invoice
  expiry plus payment and notification latency: a customer who fetched the
  invoice just before offer expiry pays a merchant that has already claimed the
  funds, and nacking that payment creates the very reconciliation case the
  protocol exists to avoid. An order with no `offer_absolute_expiry` never
  becomes `order_expired`.
- Verify that the relayed plaintext is byte-for-byte identical to the
  `sealed_order` plaintext it sealed for that order, comparing `order_metadata`
  in constant time. Otherwise the reason code is `token_mismatch`.
- Verify that `amount_msat` is at least that order's expected amount. Otherwise
  the reason code is `amount_insufficient`.

A notification failing any of these MUST NOT cause the order to be treated as
paid. Whether the PoS answers at all is governed by [Reply
Path](#reply-path).

Comparing the whole plaintext, rather than `order_metadata` alone, also catches
a relayed `amount` or `description` that does not match the order, and — since
`notification_path_hash` is part of the sealed plaintext — a merchant that sent
one order's token down another order's path. The role of `order_metadata` in
authenticating the notification is described in [Authentication and Forgery
Prevention](#authentication-and-forgery-prevention).

#### Reply Path

The PoS has no payment channels and no gossip view of the network, so it
cannot construct a route back to the merchant on its own. Per BOLT 4, an onion
message recipient can only respond over a `reply_path` supplied by the sender,
and it replies by delivering the onion directly to the path's `first_node_id`.
Accordingly:

- The merchant MUST include a `reply_path` in every `payment_notification`.
- The merchant MUST express the `reply_path`'s `first_node_id` in pubkey form
  (not the short-channel-id form, which only a node with gossip can resolve),
  and SHOULD root the path at the introduction node of the `notification_path`
  it is sending over — a node the PoS is demonstrably reachable from — or at
  another node it has reason to believe the PoS can reach. A reply address the
  PoS cannot deliver to is as good as none.
- The PoS MUST send its response, if any, over that `reply_path`; it has no
  other means of replying. It MAY drop a `reply_path` whose `first_node_id` it
  cannot reach.
- If a `payment_notification` arrives without a `reply_path`, the PoS SHOULD
  still process it — the payment may be genuine — but it has no way to
  respond, so a merchant that omits the `reply_path` will exhaust its retries
  and escalate to manual reconciliation.

Responses are as unauthenticated as notifications are: onion messages carry no
sender authentication, and the merchant's `offer_paths` are in the template,
which may be public. An `ack` the merchant wrongly attributes to a pending
notification silences the retry loop for a payment that never reached the PoS;
a forged `nack` flags a genuinely paid order for manual reconciliation. So
correlation is normative on the merchant side:

- The merchant MUST construct a fresh `reply_path` for each
  `payment_notification` — fresh per notification, not necessarily per retry —
  and place an identifier for that notification (e.g., a `path_id`, per BOLT 4)
  in the path's recipient data, mirroring how the PoS uses `order_metadata` in
  the `notification_path`. A `reply_path` MUST NOT be reused for a different
  notification, and the merchant MUST NOT reuse its `offer_paths` as a
  `reply_path`.
- `notification_ack` and `notification_nack` MUST echo the `payment_hash` of the
  notification they respond to, so correlation does not rest on the path alone.
- The merchant MUST discard a response that does not arrive on a `reply_path` it
  constructed for a notification still awaiting acknowledgement, or whose echoed
  `payment_hash` does not match that notification.

Retries of the same notification MAY reuse the original `reply_path` or carry a
fresh one; the merchant SHOULD accept a response over any `reply_path` it
constructed for that notification while it remains unacknowledged.

The PoS MAY decline to respond to a notification that fails the checks in
[Notification Payload](#notification-payload), and SHOULD rate-limit responses
to failing notifications — though it SHOULD answer `unknown_order` at least once
per arrival path, since that is the one nack the merchant acts on (a genuine
state loss is worth reporting; the merchant's `unknown_order` retry does not
reset its overall retry budget). A nack is otherwise only useful to an honest
merchant, which is retrying anyway; answering every forged notification lets a
bystander who photographed the QR code probe order state through the reason
codes, and makes the PoS originate traffic on demand. The PoS MUST NOT suppress
its first response for a given (order, `payment_hash`) that passes the checks
(an unreachable `reply_path`, per above, excepted) —
otherwise anyone holding the offer could flood the path with forgeries to starve
the one acknowledgement the merchant is waiting for — but MAY rate-limit repeats
of a response it has already sent: onion messages have no replay protection, so
a hop that captured a passing notification can replay it verbatim, and an
unconditional response obligation would make the PoS an unbounded reflector.
(Hop-level rate limiting can still drop the genuine notification itself; that is
a liveness risk the merchant's retry-and-escalate behavior covers.)

### Authentication and Forgery Prevention

Onion messages carry no sender authentication, and the `notification_path`
ships inside the offer, so any party holding the per-order offer can send a
`payment_notification` down it. The cleartext offer fields (`amount`,
`description`) are known to the customer, and the payload's
`payment_hash`/`preimage` authenticate nothing on their own: the PoS never
sees the invoice, so it cannot distinguish a real preimage from a random one.
The notification's authenticity therefore rests entirely on `order_metadata`.

**Forged notifications**: `order_metadata` exists in exactly three forms on the
wire, and each is readable by one party only:

- inside the blinded path's recipient data, encrypted to the PoS
- inside the `payment_token`, encrypted to the merchant
- inside a `payment_notification` payload, onion-encrypted to the final hop of
  the bound `notification_path` — again the PoS. This relies on onion message
  payload confidentiality: the introduction node and intermediate hops of the
  notification path cannot read the payload, so an attacker occupying the PoS's
  introduction node forwards the notification without learning anything from it.

So the only way a `payment_notification` can carry the correct `order_metadata`
is if the merchant decrypted this order's token. Three sets of requirements keep
that statement true, and all three are needed:

- The PoS MUST NOT treat an order as paid unless the relayed plaintext matches
  what it sealed for the order that owns the arrival path (see [Notification
  Payload](#notification-payload)).
- `order_metadata` must be unguessable, per [Notification
  Path](#notification-path). A value the customer can guess — an order counter,
  a timestamp, the expected amount — lets the customer forge the paid signal and
  walk away with unpaid goods. Guessing a 128-bit secret is also what makes the
  `token_mismatch` nack useless as a brute-force oracle for it.
- The merchant must not leak the decrypted secret, and must only ever send it
  down the path bound into the token, per [Merchant
  Requirements](#merchant-requirements). The merchant is the one other party
  holding the plaintext, and it decrypts on demand for anyone who sends an
  `invoice_request`; without those requirements an attacker can have the
  merchant hand the secret straight to a path of its own choosing.

**Token provenance**: the `payment_token` ciphertext proves nothing about who
created it. `Enc` is to the merchant's public `offer_issuer_id`, and the offer
template may be public, so anyone can seal a self-consistent token over fields
of their choosing. What the token guarantees instead is confidentiality and
integrity: a re-sealed token cannot contain the correct `order_metadata`,
because the tamperer never sees it, and — because `Enc` is authenticated
encryption — a genuine token cannot be modified in place either, so an attacker
cannot alter the sealed `amount` while preserving the sealed secret.

**Amount tampering**: A customer who tampers the offer amount before paying is
handled as follows. The merchant MUST reject an invoice request whose cleartext
offer fields do not match the decrypted token, and MUST NOT invoice less than
the token's `amount` (see [Merchant Requirements](#merchant-requirements)).
These are consistency checks, not authentication: a customer who re-seals the
token over the tampered fields passes them. The authoritative check is at the
PoS, where the re-sealed token fails the plaintext match above and the
notification is rejected with `token_mismatch`, so the tampered order is never
shown as paid; a genuine notification reporting a short `amount_msat` is
rejected with `amount_insufficient`. By that point the merchant has already
claimed the tampered payment, so — per the nack rules — it escalates to manual
reconciliation rather than retrying.

### Trust Model

The protocol authenticates notifications against a malicious customer; it does
not protect the PoS against the merchant node. The PoS trusts the merchant for
the truthfulness of `amount_msat`, for the notification being sent at all, for
notifications being sent only for orders actually paid, and for keeping
`order_metadata` confidential. The last two follow from the merchant holding the
decrypted token: it can forge a fully authenticated notification for an unpaid
order, and disclosing the secret would let any offer holder do the same. A
cooperating customer's [payment proof](#payment-proof) removes the trust in the
notification being sent at all, since the proof is merchant-signed and
order-bound; it does not remove trust for notifications the merchant fabricates.

Nor does the protocol bound *who* may ask the merchant to invoice a per-order
offer. Anyone holding the template — which may be public via BIP 353 — can seal
a token of their own and have the merchant issue an invoice, claim payment, and
send a notification to a path they chose. They learn nothing (the secret in that
token is their own) and the merchant is paid, but the merchant's order book and
reconciliation queue can be polluted at the cost of the sealed amount. Binding
requests to the PoS would take an authentication cookie in `offer_metadata`,
keyed at template hand-off; see [Open Questions](#open-questions).

### Payment Proof

The customer MAY send a `payment_proof` onion message to the PoS via the
notification path. This sender-side extension provides redundancy (if the
merchant's notification fails) and prevents the merchant from denying payment.
The PoS never sees the invoice, so the proof is what lets it verify the payment
independently of the merchant.

The proof payload is a BOLT 12 payer proof as defined in
[bolts#1295](https://github.com/lightning/bolts/pull/1295): a redacted copy of
the invoice TLV stream that carries the invoice node's `signature`, the
`proof_preimage`, and a `proof_signature` from the customer's `invreq_payer_id`.

The PoS MUST accept a `payment_proof` only if:

- The payer proof is valid per the reader requirements of bolts#1295
- The proof arrived on a notification path the PoS constructed, identifying an
  order via the path's `order_metadata`
- `invoice_node_id` matches the `offer_issuer_id` of the template that order's
  offer was built from — not merely some template the PoS knows
- The proof discloses the invoice `payment_token` TLV, and it is byte-for-byte
  identical to the `payment_token` ciphertext the PoS sealed into the offer for
  that order. A proof disclosing no `payment_token` MUST be rejected.
- `invoice_amount` is included and is at least that order's expected amount

A customer sending a `payment_proof` MUST NOT redact the invoice
`payment_token` or `invoice_amount` TLVs from the proof; a proof missing either
cannot be checked and will be rejected. Note that `payment_token` has a type
number defined by this bLIP, so a wallet implementing only bolts#1295 may treat
it as unknown.

The proof cannot pin the payment's chain: the proof is a redacted TLV stream and
the payer chooses what to redact, so a check on a disclosed `invreq_chain` would
be voluntary. The denomination instead rests on the merchant's `invoice_request`
checks (see [Merchant Requirements](#merchant-requirements)) — a merchant-signed
invoice embedding the order's token exists only if those checks passed, and a
merchant that missigns is already outside the [Trust Model](#trust-model).

An accepted proof marks the order paid, exactly as a passing notification does:
a `payment_notification` subsequently arriving for that order is re-acked under
the already-paid rule in [Notification Payload](#notification-payload). The same
expiry treatment applies as for notifications.

The ciphertext equality check binds the proof to the order it arrives for.
`order_metadata` is fresh per order, so no two orders share a `payment_token`
ciphertext, and a valid proof for one order cannot confirm another: paying a
cheap order A and replaying its (valid) proof down order B's notification path
fails, because the proof discloses order A's token rather than the one sealed
for B. The PoS compares against the ciphertext it produced at offer
construction, so the check requires no decryption. Binding `invoice_node_id` to
the order's own template matters for the same reason: a PoS serving several
merchants (or holding a rotated template) would otherwise accept a proof signed
by a *different* merchant's node over an invoice that embeds this order's
ciphertext.

## Rationale

### Why Not LNURL/LUD-21?

LNURL with LUD-21 requires a centralized callback server, does not provide
proof-of-payer, and introduces privacy trade-offs. This protocol is fully
decentralized and builds on BOLT 12's existing infrastructure.

## Open Questions

1. **Proof of payment**: Resolved by adopting BOLT 12 payer proofs
   ([bolts#1295](https://github.com/lightning/bolts/pull/1295)) for the
   [payment proof](#payment-proof), which bind the preimage to the
   merchant-signed invoice and add proof of payer via `proof_signature`. It
   remains open whether the merchant should also be able to forward a
   payer-proof-like attestation directly, for customers whose wallets do not
   support payer proofs.

2. **Async payments**: Offline merchants cannot receive payments or send
   notifications. Deferred.

3. **Authenticating the invoice request to the merchant**: the merchant cannot
   currently tell a PoS-issued per-order offer from one any template holder
   sealed itself (see [Trust Model](#trust-model)). BOLT 12 reserves
   `offer_metadata` for exactly this — an authentication cookie over the other
   offer fields — so the PoS could MAC the per-order fields under a key shared
   at template hand-off, and the merchant could reject requests that fail to
   verify. This would also let the merchant reject expired orders, which are
   likewise unauthenticated today. Whether to require it is open.
